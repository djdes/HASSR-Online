# Ограничение автоматического обхода страниц

`src/proxy.ts` применяет `page-navigation-guard.ts` после существующих проверок прав. Частый обход получает HTTP 429 с русским экраном ожидания, `Retry-After`, `no-store` и `noindex`. Проверка работает на сервере; отключение JavaScript и изменение кнопки не снимают блокировку. Повтор открывает тот же URL. Для отказа на RSC-запрос установленный Next.js 16.1.6 переключается на загрузку документа, где показывается экран ожидания.

Пороги намеренно мягкие (`PAGE_NAVIGATION_LIMITS` в `src/lib/page-navigation-limit.ts`, ослаблены 2026-10-26 после жалоб на ложные срабатывания): человек, листающий страницы, до них не доходит, их достигает только обход со скоростью машины. Обычный клиент: 100 загрузок документов за скользящие 10 секунд, 400 за минуту. Пустой user-agent и признаки curl/wget/python-requests/HeadlessChrome и подобных инструментов снижают пороги до 20/90. Минутный предел каждого бюджета меньше шести 10-секундных, иначе он ничего бы не ограничивал. Сам user-agent не запрещает доступ и не даёт исключений: подмена имени браузера сохраняет бюджет. Пауза — 15 секунд, повторные запросы её не продлевают. Все RSC-запросы (предзагрузка и клиентские переходы Next.js) имеют отдельный предел 1200/минуту и общую паузу. Причина: Next 16.1.6 при полной предзагрузке не всегда отправляет маркер prefetch. Подмена `RSC: 1` выбирает этот ограниченный бюджет, но не отменяет проверку; маркер prefetch на обычном документе не даёт исключения.

Проверяются GET страниц, включая RSC. Исключены API, внутренние ресурсы Next.js, публичные статические файлы, OG-картинки, `.well-known`, `/payment`, `/invite`, `/equipment-fill`, `/room-fill`, `/task-fill`, `/kiosk` и их подпути. Другие методы не затрагиваются. Ограничитель не заменяет существующую защиту регистрации, авторизацию и ограничения API.

Прогрев после деплоя (`scripts/prewarm-routes.sh`, около 70 страниц подряд curl'ом с самого сервера) иначе попадал бы в общий бюджет `unknown` и после шестого адреса получал 429, не загружая страницы. Поэтому деплой перед `pm2 start` создаёт случайный ключ `DEPLOY_WARM_TOKEN` (32 байта), процесс сайта получает его в окружении, а прогрев шлёт его в заголовке `x-deploy-warm`. Запрос с точно совпавшим ключом (сравнение постоянного времени) не ограничивается и не тратит бюджет; остальные проверки proxy для него прежние. Ключ меняется на каждом деплое, не пишется в лог и не передаётся в аргументах curl. Без ключа в окружении (dev, тесты) или с ключом короче 32 символов исключений нет.

В реальном proxy Next.js удаляет служебные Flight-заголовки. Для выделения фоновых запросов используется стандартный `Sec-Fetch-Dest: empty` (и `RSC: 1`, когда он виден обработчику). Запрос без этих признаков получает более строгий лимит документов. Поддельный Fetch Metadata также не снимает ограничение 1200/минуту.

## Доверие к адресу

Для вошедшего пользователя ключом служит ID из проверенного JWT (разные сотрудники за одним NAT независимы). Для гостя — проверенный IP из `X-Real-IP`, запасной вариант — последний адрес `X-Forwarded-For`, добавленный доверенным прокси. Произвольные строки и IPv6 zone ID не принимаются; IPv6 приводится к единой форме. Отсутствующий/некорректный адрес попадает в общий бюджет `unknown`. Cookie и произвольный заголовок пользователя не создают новый бюджет.

**Условие размещения:** Nginx должен перезаписывать `X-Real-IP` значением своего доверенного адреса клиента (`$remote_addr` при прямом подключении) и корректно добавлять peer в XFF; порт приложения доступен только доверенному прокси. При CDN цепочку доверенных прокси нужно настроить явно. Перед публикацией проверить фактическую конфигурацию ingress. Прямой доступ к origin с самостоятельно заданным `X-Real-IP` обходит разделение по IP.

## Границы защиты

Состояние находится в памяти одного процесса: текущая схема — один web-процесс PM2. Перезапуск сбрасывает бюджеты; перед несколькими процессами/серверами нужен общий store (например Redis). Не более 5000 субъектов, максимум 400 временных меток страниц и 1200 предзагрузок на субъект. Неактивные записи удаляются при периодической минутной очистке. При заполнении памяти новые субъекты получают ожидание до следующей очистки (до 60 секунд), существующие бюджеты не вытесняются. Это режим перегрузки, отдельный от обычной 15-секундной паузы.

Гости за одним NAT делят бюджет; входящие аккаунты получают отдельный. Распределённый/медленный обход, смена IP, множество действительных аккаунтов и уже загруженные браузером страницы эта мера не останавливает. Доступные пользователю HTML, JS и изображения невозможно полностью защитить от копирования. Детектор замедляет быстрый массовый обход без внешнего CAPTCHA/CDN-сервиса. Идентификаторы, IP и URL не выводятся на экране ожидания и не логируются этим модулем.
