# Откат обмена справочниками: версии отпечатка связей

Серия C2 (#276, 2026-11-20) ввела версии состава полей обмена: помещения переносятся с графиками уборки и нормами климата, должности — с журналами (`ENTITY_FIELD_VERSIONS` в `src/lib/directory-exchange/kinds.ts`). Первый же обмен после выката перевёл связи помещений и должностей на отпечаток новой версии: `v2:…`, а у должностей с компанией другого аккаунта — `f:v2:…`.

Код до C2 версий не знает. Для него `v2:…` — обычный отпечаток, он не совпадёт с отпечатком записи, и **каждое помещение и каждая должность будут выглядеть правленными**: обмен начнёт переписывать записи одних организаций записями других. Поэтому простой `git revert` небезопасен — сначала отпечатки связей пересчитываются в составе прежней версии.

## Когда нужен

- revert серии C2 (#276);
- revert любой правки, которая добавила новую версию состава полей в `ENTITY_FIELD_VERSIONS` (тогда — к той версии, что была до неё: `--to-version=N`).

Обычная правка кода обмена без новой версии состава полей скрипта не требует.

## Что делает скрипт

`scripts/directory-exchange-hash-downgrade.ts` (правила — `src/lib/directory-exchange/hash-downgrade.ts`, работа с базой — `hash-downgrade.server.ts`):

- берёт связи сущностей, у которых нынешняя версия выше целевой (сейчас — помещения и должности), с отпечатком новой версии;
- читает запись так же, как её видит обмен (поля и группа родителя — объекта у помещения — по связям того же кабинета и организации);
- если запись не правили после последнего обмена (её отпечаток в версии связи совпадает с отпечатком связи), пишет отпечаток прежней версии — ровно тот, что считает код до правки. У должности «между аккаунтами» метка `f:` снимается: в версии 1 у должностей такого состава не было;
- по умолчанию — **пробный прогон**: только отчёт по кабинетам, в базу ничего не пишется;
- `--apply` — запись: по кабинету **в одной транзакции под замком обмена**; план пересчитывается уже под замком, пишется только связь, чей отпечаток всё ещё прежний. Кабинет, занятый обменом, пропускается с сообщением «ЗАНЯТ», и скрипт завершается с кодом 1 — запустите его ещё раз;
- повторный `--apply` — 0 изменений.

Не трогает:

| Связь | Почему |
|---|---|
| надгробие (запись удалили) | отпечаток не сверяется |
| уже прежней версии | нечего делать |
| версия новее кода | посчитать нечем |
| запись не найдена | следующий обмен сделает надгробие |
| запись правили после последнего обмена | связь остаётся новой версии, и код до отката увидит правку и разнесёт её — правка не теряется молча (как разнёс бы её и нынешний код) |

Ключи: `--apply` — записать; `--cabinet=<id>` — только один кабинет (попробовать сначала на нём); `--to-version=N` — к какой версии (по умолчанию 1). Коды выхода: 0 — готово, 1 — кабинет занят или ошибка, 2 — неверные ключи.

## Порядок отката

Прод выкатывается **только из `master`** (AGENTS.md, «Production deploy rules»): никаких веток, тегов, ручной сборки на сервере. Откат — это `git revert` на `master`, а скрипт запускается на сервере **до** выката отката, пока работает нынешний код.

1. **Подготовить revert, не сливая.** Ветка от свежего `origin/master`, `git revert <коммит C2>` (squash-коммит — обычный revert). В том же коммите:
   - удалить то, что опирается на версии состава: `src/lib/directory-exchange/hash-downgrade.ts`, `hash-downgrade.server.ts`, `hash-downgrade.test.ts`, `scripts/directory-exchange-hash-downgrade.ts`;
   - убрать из ночного прогона сценарии C2: `scripts/e2e/versioning-check.ts`, `scripts/e2e/new-lists-check.ts` (и их строки в `scripts/e2e/run-all.sh`);
   - разрешить конфликты с более поздними сериями.

   `npm run typecheck` и `npm run test:gate` зелёные, PR зелёный и готов к слиянию.
2. **Пробный прогон на сервере** — из каталога приложения (`/var/www/wesetupru/data/www/wesetup.ru/app`), не около 04:00 МСК (плановый обмен):

   ```bash
   npx tsx scripts/directory-exchange-hash-downgrade.ts
   ```

   Отчёт: по каждому кабинету — сколько связей переписать (по помещениям и должностям) и сколько оставлено и почему.
3. **Запись:**

   ```bash
   npx tsx scripts/directory-exchange-hash-downgrade.ts --apply
   ```

   Код выхода 1 («ЗАНЯТ» или ошибка) — запустить ещё раз, пока не будет 0. Затем пробный прогон ещё раз — должно быть «Связей к записи: 0».
4. **Сразу слить revert в `master`** — push в `master` выкатывает его.

   Пока выкат идёт, работает ещё нынешний код: обмен, запущенный в эти минуты (кнопка «Обменяться», сохранение настроек обмена, подтверждение запроса), снова переведёт связи своего кабинета на версию 2 — без правок записей, но после выката код до C2 сочтёт их правленными. Поэтому шаги 3 и 4 — подряд, без перерыва.
5. **После выката — проверка** (только чтение):

   ```sql
   SELECT "masterOrganizationId", entity, count(*)
   FROM "DirectoryExchangeLink"
   WHERE entity IN ('room', 'position') AND "entityId" IS NOT NULL
     AND (hash LIKE 'v%' OR hash LIKE 'f:v%')
   GROUP BY 1, 2;
   ```

   Строк столько, сколько в отчёте `--apply` было «правили после обмена» и «записи нет» (обычно ни одной). Если у кабинета их больше — в окне шага 4 у него прошёл обмен: код до C2 при следующем обмене этого кабинета заново согласует группы помещений и должностей по самой свежей записи (название, вид и порядок помещения, название должности — обычно те же значения). Проверьте итог его обмена в карточке «Обмен справочниками».

## Что ещё меняется при откате C2

- **Разовые переносы**, сделанные после C2, хранят отпечатки созданных помещений и должностей версии 2. Код до C2 при «Отменить перенос» сочтёт такие помещения и должности правлеными и оставит их — ничего лишнего не удаляется, оставшееся можно удалить вручную.
- **Списки «Журналы» и «Чек-листы»** до C2 не существуют: код до C2 их отметки у участников не видит, связи остаются в базе без дела. Если владелец пересохранит настройки обмена, отметки этих списков пропадут — после повторного выката C2 их нужно будет включить заново.
- **Графики уборки, нормы климата и журналы должностей**, уже разнесённые обменом, остаются у организаций как есть — откат перестаёт переносить их дальше, но ничего не стирает.
