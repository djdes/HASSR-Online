# Уведомления администратора в Telegram

Уведомления онлайн-чата, регистраций, оплат, обращений, партнёрских заявок, отзывов и служебных ошибок используют `notifyPlatformAdmin` → общий Telegram-транспорт. Получатели берутся из `PLATFORM_ADMIN_TELEGRAM_CHAT_ID` и совместимой `FEEDBACK_ADMIN_TG_CHAT_ID`; оба списка объединяются.

Если процесс бота работает, а уведомления не приходят, это ещё не подтверждает связь с Telegram. Проверка доступна по `/api/telegram/health`, а `/api/healthz` использует тот же транспорт, что отправка уведомлений.

## Частный HTTP-прокси

В настоящем `.env` сервера задаётся:

```dotenv
TELEGRAM_PROXY_URL="http://USER:PASSWORD@HOST:PORT"
```

Это HTTP CONNECT: запросы Telegram проходят через прокси с обычной проверкой TLS-сертификата Telegram. Прокси применяется к обоим клиентам бота и вложениям. Другие интеграции приложения используют свои обычные подключения. При настроенном прокси `TELEGRAM_FORCE_IP` не используется для Telegram.

Значение с паролем хранится только в закрытом `.env`. В `.env.shared` оставлен пустой пример. При смене доступа нужно обновить `.env` и перезапустить **оба** процесса с обновлённым окружением: `haccp-online` и `haccp-telegram-poller`. Простого изменения `.env` недостаточно: PM2 может сохранять прежнее окружение.

Проверить результат:

1. `/api/telegram/health` возвращает `ok: true` и `wesetupbot`.
2. `/api/healthz` показывает успешные проверки БД и Telegram.
3. В кабинете администратора: `/root/feedback` → «Проверить связь». Тест должен прийти всем настроенным администраторам.
4. Сообщение через онлайн-чат сайта должно появиться в Telegram с тегом `#chat_…`.
5. Ответить свайпом на это сообщение: ответ должен появиться в исходном чате.

Процесс получения сообщений запускается с `drop_pending_updates: false`: при перезапуске сохранённые Telegram входящие сообщения не удаляются. Совместимость сигналов отмены и потоковых файлов обеспечивается `src/lib/telegram-fetch.ts`.

## Восстановление накопившихся уведомлений

Из каталога приложения на сервере:

```bash
npx tsx scripts/recover-admin-telegram.ts --since 2026-09-30
```

Без `--send` команда только показывает число сохранённых неудачных отправок по типам событий и маскам получателей. Тексты обращений, адреса пользователей и секреты в вывод не попадают.

После восстановления связи и проверки предварительного списка:

```bash
npx tsx scripts/recover-admin-telegram.ts --since 2026-09-30 --send
```

Отправляются только записи со статусом `failed` или `rate_limited` для настроенных администраторов. Уведомления, уже доставленные ранее, не повторяются. Перед каждой отправкой запись атомарно переводится в `queued`, поэтому параллельный или повторный запуск не дублирует обработанный список. Темп ограничен; временные ошибки и 429 повторяются до трёх попыток.

К тексту добавляется дата исходного события по Москве. Теги `#chat_…` и `#fb_…` сохраняются: на восстановленные обращения можно отвечать свайпом. Если исходный текст уже занимает весь лимит Telegram, он отправляется целиком без дополнительного заголовка.

Подтверждённая доставка записывается в исходную строку `TelegramLog` (`sent`, `sentAt`); успешные обращения также получают отметку доставки в `FeedbackReport`. Если Telegram подтвердил отправку, но БД не записала подтверждение, строка отмечается `recovery_uncertain` и автоматически не повторяется.

Скрипт восстанавливает сохранённые тексты. Если в предварительном списке есть строки `[attachment]`, он останавливается перед отправкой: сами файлы нужно восстановить по метаданным исходного обращения. Сообщения, которых нет ни в БД, ни в очереди Telegram, нельзя получить из этих источников.

Технические сведения о транспорте: [ProxyAgent — официальный Undici](https://github.com/nodejs/undici/blob/main/docs/docs/api/ProxyAgent.md).
