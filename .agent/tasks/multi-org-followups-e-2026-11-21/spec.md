# Spec (frozen 2026-11-21): серия E — эксплуатация обмена, управляющий сетью, деньги сети

Владелец 21.11.2026 после серии D (#278): «Сделай все кроме: 12» из 12 предложенных. Берём пункты 1–11.

## Решения

### Р1. Тревога о сбоях обмена (п. 1)
После планового обмена (`runAllDirectoryExchanges`) — одно сообщение владельцу платформы (`notifyPlatformAdmin`), если
есть кабинеты с ошибкой в этом прогоне или без успешного обмена за 24 часа: число, названия (до 10), ссылка на
`/root/directory-exchange`. Не чаще раза в сутки (отметка в журнале действий). Сбой отправки обмен не ломает.

### Р2. Сквозные сценарии на PR (п. 2)
Тот же рабочий процесс, что ночной (`nightly-e2e.yml`), запускается и на `pull_request` в master при изменениях в
`src/lib/directory-exchange/**`, `src/lib/balance/**`, `src/lib/org-trial*`, `src/lib/billing.server.ts`, `scripts/e2e/**`,
`prisma/schema.prisma`; оповещение в Telegram — только для ночного запуска.

### Р3. Нагрузочная проверка обмена (п. 3)
Сценарий `scripts/e2e/load-exchange.ts` (не в ночном наборе): кабинет, 20 организаций, 5 000 товаров, 500 сотрудников,
50 объектов и 300 единиц оборудования; первый обмен и повторный (без изменений) — время и пиковая память. Цель: первый
обмен ≤ 10 минут (замок обмена держится до 10 минут), повторный ≤ 60 с, память процесса ≤ 1,5 ГБ. Не укладывается —
убрать очевидные лишние запросы (пакетная загрузка, `createMany`), без смены поведения. Итоги — в evidence.

### Р4. Уборка служебных таблиц (п. 4)
При плановом обмене: пропуски, которые не видели 30 дней или чья организация больше не участвует этим списком;
запросы другой компании в статусах «отклонён / отменён / истёк» старше 180 дней; записи о разовых переносах старше 180
дней (отмена — 7 дней). Число удалённых — в итоге планового обмена.

### Р5. Управляющий сетью (п. 5)
Таблица `AccountNetworkManager` (аккаунт, пользователь, кто назначил, когда). Владелец аккаунта на странице «Сеть»
назначает управляющего из руководителей организаций аккаунта (с полным доступом) и снимает. Управляющий получает права
владельца на: страницу «Сеть», настройку и запуск обмена, разовый перенос и его отмену, разбор пропусков, историю и её
отмену, код мастер-кабинета, баланс по аккаунту и переводы между организациями. Только владелец: решение по запросам
другой компании, назначение управляющих, тариф и оплата. Все действия — в журнале с именем управляющего. «Войти как» и
точечный доступ — как у владельца, отказ.

### Р6. Сводка по сети за период (п. 6)
На странице «Сеть» — переключатель «Сегодня / 7 дней / 30 дней»: по организации — доля дней, в которые обязательные
журналы заполнены, и число записей журналов за период; выгрузка таблицы в Excel (`exceljs`) и PDF (`jspdf`, как
остальные выгрузки). Расчёт ограничен (до 50 организаций, без пересчёта каждого дня по всем шаблонам, если есть дешёвый
источник — использовать его; иначе — по дням из записей журналов).

### Р7. Еженедельный дайджест обмена (п. 7)
Раз в неделю (существующая еженедельная задача) владельцу аккаунта и управляющим сети с обменом: по организациям —
сколько пришло (создано / изменено) за 7 дней, сколько ждёт разбора, ошибки обмена; ссылка на карточку «Обмен
справочниками». Письмо и Telegram (`sendOwnerNotice`-подобно), только если есть что сообщить; без повтора за неделю.

### Р8. «Сеть» в мини-приложении (п. 8)
Страница мини-приложения Telegram (`src/app/mini/network`) для владельца и управляющего: компактный список организаций
(журналы сегодня, баланс, свои 14 дней), переход в организацию; пункт в разделах мини-приложения, если сеть 2+.

### Р9–Р10. Оплата из балансов организаций аккаунта (пп. 9, 10)
Тариф и точки — на аккаунт, деньги — на балансах организаций. На странице тарифа, если на балансе активной организации
не хватает на выбранную оплату, а по аккаунту хватает, — кнопка «Собрать с организаций аккаунта и оплатить»: недостающее
переводится существующим переводом между своими организациями (сначала с самых больших балансов, ключи повтора), затем
обычная оплата с баланса. Подтверждение показывает, сколько и откуда. Только владелец аккаунта. Напоминание о конце
своих 14 дней (и ссылка «Добавить точку») ведёт туда же; если по аккаунту денег хватает — текст напоминания говорит об
этом. Сбой оплаты после переводов — деньги остаются на балансе активной организации (переводы видны в истории).

### Р11. Сценарии без дублей (п. 11)
Скрипты в `.agent/tasks/*/raw/*.ts`, у которых есть копия в `scripts/e2e/`, заменяются короткими обёртками, которые
запускают `scripts/e2e/<имя>.ts`; журналы-доказательства остаются.

## Критерии приёмки
- AC1. Тревога: сбой и «сутки без успеха» → одно сообщение в сутки; нормальная ночь — ничего.
- AC2. Рабочий процесс на PR проходит синтаксическую проверку; условия путей верны.
- AC3. Нагрузочная проверка: числа в evidence; цели выполнены или причины и меры описаны.
- AC4. Уборка удаляет только старое/ненужное; сквозная проверка.
- AC5. Управляющий: может всё из списка, не может решать запросы другой компании, назначать управляющих и платить;
  снятие управляющего сразу отбирает права; не управляющий — 403/404. Сквозная проверка по API.
- AC6. Период: значения сходятся с данными; Excel и PDF открываются (проверка содержимого).
- AC7. Дайджест: письмо/Telegram при событиях, ничего при пустой неделе, без повтора.
- AC8. Мини-приложение: страница для владельца и управляющего, остальным — нет.
- AC9. Сбор и оплата: при нехватке на активной и достатке по аккаунту — переводы и оплата, итог сходится, ключи
  повтора; при нехватке по аккаунту — кнопки нет; не владелец — отказ.
- AC10. Обёртки запускают те же сценарии; ночной набор зелёный.
- AC11. Схема — только добавления (`AccountNetworkManager`); тексты ru/en/uz; typecheck, test:gate, eslint, i18n:check;
  `npm run e2e:exchange` зелёный; живой прогон.
