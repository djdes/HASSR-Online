# Spec (frozen 2026-09-27): фотофиксация показаний — «Сфотографируйте показание» первым действием на QR-наклейке

Диалог владельца с клиентом: заведующая сканирует QR холодильной камеры, вводит PIN — а там кнопка
«Сфотографируйте показание»: сфотала — показание само считалось, ввелось и зафиксировалось, фото легло в базу
(минус человеческий фактор). Не захотела фотать — ввела по старинке; организации не надо — сняли галочку, кнопка
пропала. Клиент: «не во всех холодильниках электронные термометры, видел раритеты 80-х» — владелец: «и с ртутным
справимся». Решение: через диспетчер, «как получится, потом поправим».

Уже есть (задача `temp-photo-2026-09`): у поля температуры в QR-формах холодильника (`/equipment-fill`) и склада
(`/room-fill`) кнопка «Фото» (`src/components/qr-fill/reading-photo.tsx`): снимок → `/api/qr-fill/reading-photo` →
`readingPhotos` записи журнала; на платном тарифе — распознавание `/api/qr-fill/reading-photo/recognize` (вид
`reading` диспетчера, защита от выдумывания) с пометкой «с фото — проверьте»; на бесплатном — подсказка и 402.
Строим поверх, не дублируем.

## План

1. **Фото — главное действие формы.** После выбора имени/PIN, если фотофиксация включена и значения ещё нет:
   большая основная кнопка «Сфотографируйте показание» (камера телефона), под ней «Ввести вручную» (вторичная)
   и, у холодильника, «Обслуживание / Ремонт». Поле показания и «Сохранить» появляются после снимка (или после
   «Ввести вручную»): платный тариф — число со снимка уже в поле с пометкой «с фото — проверьте», кнопка
   сохранения — «Всё верно — сохранить» (одно нажатие); нечитаемо / бесплатный тариф / ошибка — поле пустое,
   фото уже прикреплено, ввод руками. Тот же компонент `ReadingPhoto` (вариант `primary`), без второго механизма
   загрузки. Уже записанное сегодня значение или восстановленный черновик — сразу поле (как сейчас) и маленькая «Фото».
2. **Настройка организации** «Настройки → Строгость журналов → Запись по QR-плакату»: «Фотофиксация показаний»
   (вкл. по умолчанию; выкл. — кнопок «Сфотографируйте показание»/«Фото» нет, ввод как раньше) и вложенная
   «Фото обязательно» (без снимка температуру не сохранить; «Обслуживание/Ремонт» и влажность — без фото).
   **Хранение без изменения схемы:** общего JSON-поля настроек у организации нет — у каждого JSON-поля
   (`customNamesJson`, `journalTaskModesJson`, `journalAutomationJson`, …) свой разборщик, который выбрасывает
   чужие ключи, и свой писатель, который перезаписывает объект целиком: чужой флаг там молча пропал бы при
   сохранении соседней настройки. Поэтому — существующая таблица ключ-значение `PlatformSetting`, ключ
   `org-reading-photo:<orgId>`, значение JSON `{"enabled":bool,"required":bool}`; нет строки — `{enabled:true,
   required:false}`. Весь доступ — в `src/lib/reading-photo-settings*.ts` (перенос в колонки организации позже —
   правка двух функций; предложение в отчёте, схему сейчас не трогаю).
3. **Сервер проверяет сам, не интерфейс:** фотофиксация выключена — загрузка и распознавание фото → 403
   `photo_disabled`, присланная ссылка на фото при сохранении игнорируется; «Фото обязательно» — сохранение
   температуры без фото → 400 `photo-required` (оба маршрута: `/api/equipment-fill/[id]`, `/api/room-fill/[id]`).
   Тариф для автоввода — как есть (402 `paid_only`).
4. **Аналоговые термометры.** Инструкция вида `reading`: сначала тип прибора (`device`: digital / dial / liquid /
   other), правила чтения 7-сегментного дисплея (минус — отдельный сегмент слева, десятичная точка), стрелочного
   (куда указывает стрелка между подписанными делениями °C, подписи ниже нуля бывают без минуса), жидкостного
   (верх столбика по шкале °C, шкалу °F не брать); аналог — округлить до 1 °C, confidence не выше medium;
   несколько приборов — самый крупный в центре кадра, одинаковые показания — одно значение, разные — null;
   часы, заряд, цены — не показание; не уверен — null. Сайт разбирает `device`, округляет аналог до целого и
   режет confidence (не доверяя модели). Проверка на настоящей модели — воркер `-TestImage … -TestPromptFile …`
   на 5 эталонных снимках (≤ 10 прогонов), результаты «ожидалось/получено» — в evidence. Эталонные снимки в git
   не попадают.
5. **Фаза 2 (предложение, не делаю, если не выйдет маленькой):** обход нескольких камер с одного QR журнала —
   на странице статуса у каждой камеры «Сфотографировать показание», только с фото (фото доказывает, что замер
   сделан у камеры). Уже сейчас обход 5 камер = 5 наклеек с одним PIN (пропуск 30 минут + «Следующий QR»).

## Критерии приёмки
- **AC1** QR-формы холодильника и склада (390 px): при включённой фотофиксации после PIN главная кнопка
  «Сфотографируйте показание» (≥ 48 px, `capture=environment`) и «Ввести вручную»; платный тариф (мок диспетчера):
  снимок → число в поле с пометкой → «Всё верно — сохранить» одним нажатием → запись с фото в журнале;
  нечитаемо/бесплатный — поле для ручного ввода, фото прикреплено; «Ввести вручную» — как раньше.
- **AC2** Настройка «Фотофиксация показаний» / «Фото обязательно» (1440 px): переключается и сохраняется;
  выключено — в QR-формах нет ни большой кнопки, ни «Фото», загрузка → 403; «Фото обязательно» — «Сохранить»
  неактивна с причиной «Нужно фото показания», сервер без фото → 400, с фото → 200; «Обслуживание» без фото — 200.
- **AC3** Инструкция `reading` знает цифровой, стрелочный и жидкостный термометр; разбор `device`, округление
  аналога и потолок confidence — тестами; настоящая модель на 5 эталонах: 21 → 8.4, 22 → −18…−20, 23 → 3 (3.0),
  24 → −26.3, 25 → +22…+23 (результаты и прогоны — в evidence, ≤ 10 прогонов).
- **AC4** `npm run typecheck` и `npm test` зелёные (новые тесты: настройки, решение сервера о фото, логика
  «фото первым», инструкция, разбор); ESLint по изменённым файлам без новых замечаний; evidence.md.
