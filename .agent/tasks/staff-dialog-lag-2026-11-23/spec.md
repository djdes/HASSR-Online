# «Изменить» на /settings/users открывается 2–5 с — разгрузить страницу сотрудников

- **Task ID:** `staff-dialog-lag-2026-11-23`
- **Base:** `origin/master` `fe4cce90`
- **Frozen:** 2026-11-23, before implementation.

## Запрос владельца

«Почему при нажатии на изменить у сотрудников всплывашка открывается с задержкой в 2-5 секунд, что самое странное и
по кнопке отменить тоже самое, как будто перегруз в браузере. Из-за табеля снизу и кол-ва кода на странице, может
сделать асинхронную подгрузку при скроле или как-то разграничить скрыть или облегчить. Продумай в этом разделе сайта
https://wesetup.ru/settings/users а так же в других по сайту где может такая же быть проблема, если что кешировать
что-то по запросам в БД но главное чтобы без проблем в последствии было.»

## Найденная причина (замеры до правки, `raw/`)

Организация как на скриншоте: 117 сотрудников, Сб/Вс выходные. Production-сборка, Chromium, 1920×1080, быстрый CPU
(×1). Длительность клика по Event Timing API (то же, что INP).

- «Изменить» — **880 мс**, «Отмена» — **824 мс**; при CPU ×4 (обычный ноутбук) — **4 632 / 4 216 мс**, те самые
  2–5 с.
  Галочка у сотрудника — 624 мс, одна буква в поиске — 608 мс, клетка табеля — 1032 мс.
- DOM страницы — **23 789 узлов, из них 22 562 — табель** (117 × 31 клетка, в каждой button + span + SVG-галочка +
  span для печати). HTML страницы — **4,96 МБ** (классы 1,5 МБ, SVG 1 МБ).
- Каждое открытие/закрытие окна:
  1. React перерисовывает **всю страницу вместе с табелем** (~210–260 мс): состояние окон (`dlg`, `bulkAddOpen`,
     `pairEmployee`) и поиска живёт в корневом `StaffPageClient`, табель не мемоизирован, в каждой из 3 600 клеток
     создаётся `Intl.DateTimeFormat`, 3–4 вызова `t()`, два замыкания и SVG-компонент.
  2. Браузер 2–3 раза пересчитывает стили **всех ~23 800 элементов** (~250–300 мс каждый). Причина — глобальные
     правила `:has()` с якорем на `body`/`html` (тёмная тема, «Новая» палитра, touch-варианты): вставка портала
     Radix в `<body>` инвалидирует `:has()` у `body`, и Chrome помечает «все потомки недействительны»
     (`allDescendantsMightBeInvalid`, трейс `raw/`). Вставка одного `<div>` в `<body>` на этом DOM — 258 мс.
     Эксперименты: без DOM табеля окно открывается за 336 мс, с `content-visibility: hidden` на табеле — 408 мс
     (пересчёт падает до ~1 220 элементов), без всех `:has()` — 536 мс.

## Решения

- Р1. **Окна не трогают страницу.** Состояние окон (`dlg`, массовое добавление, вход по телефону) — во «внешнем»
  хранилище (`src/lib/detached-state.ts`): страница получает стабильный сеттер с той же сигнатурой, перерисовывается
  только хост окон (`DetachedValue`). Поиск по ФИО — отдельный компонент со своим состоянием.
- Р2. **Табель дешёвый и мемоизированный.** `WorkOffGrid` в `memo` со стабильными колбэками (`useStableCallback`);
  строки — `memo`-компонент с примитивными пропсами (строка состояния дней, ключ недельных выходных), поэтому при
  покраске и после `router.refresh()` перерисовываются только изменившиеся строки. Данные дней (выходной, подписи)
  считаются один раз на месяц одним форматтером; обработчики клеток — один делегированный на сетку; галочка-SVG
  только в отмеченных клетках; отметка для печати — CSS `::after` вместо отдельного span. Поведение (покраска,
  Shift-прямоугольник, клавиатура, недельные чипы, сортировка, подсказки, печать) — как было.
- Р3. **Табель вне экрана не стоит ничего.** Новый `OffscreenSection`: табель монтируется, когда подходит к экрану
  (в transition, без долгой задачи), а когда уходит далеко — получает `content-visibility: hidden` с запомненной
  высотой: браузер не считает его стили и раскладку. Печать всегда видит табель (CSS `print:` + монтирование
  перед печатью).
- Р4. **Сервер отдаёт меньше.** Исключения графика (`StaffWorkOffDay`) — только за окно, которое можно открыть
  в сетке (±12 месяцев, `clampOffset`), а не за всю историю. Кэш запросов к БД не вводим: задержка была не в базе
  (ответ сервера ~0,4 с, RSC-обновление ~50 мс), а кэш данных сотрудников создал бы риск устаревших данных после
  правок.
- Р5. **Остальной сайт.** Тот же разбор для других тяжёлых экранов: в отчёте — где повторяется схема «состояние
  окна над большой сеткой» (журналы-документы), и системная причина в глобальном CSS (`:has()` на `body`/`html`) с
  замерами и планом отдельной задачи. Глобальную темизацию в этой задаче не переписываем: это затрагивает тёмную
  тему, «Новую», мини-приложение и партнёрские макеты.

## Критерии приёмки

- **AC1.** На той же базе (117 сотрудников) и том же стенде «Изменить» и «Отмена» в верхней части страницы
  укладываются в **≤ 250 мс при CPU ×1 и ≤ 1 000 мс при CPU ×4** (медиана Event Timing), против 880/824 мс и
  4 632/4 216 мс. Остаток — пересчёты стилей остальной страницы из-за глобальных `:has()` (Р5).
- **AC2.** Открытие/закрытие окна не перерисовывает табель: React-работа на клик ≤ 60 мс (трейс), пересчёт стилей
  при открытии окна вверху страницы не затрагивает табель (элементов в самом большом пересчёте ≤ 3 000).
- **AC3.** Табель ведёт себя как раньше: покраска мышью (включая протяжку и Shift), клавиатура Enter/Пробел,
  недельные чипы, сортировка, смена месяца, подсказки, печать (отметки на бумаге), пустое состояние —
  проверено в браузере; размер HTML страницы уменьшился минимум вдвое.
- **AC4.** Сервер загружает `StaffWorkOffDay` только за окно ±12 месяцев; чистая функция окна покрыта тестом.
- **AC5.** Новые примитивы (`detached-state`, `useStableCallback`, `OffscreenSection`) покрыты тестами, где это
  чистая логика; `npm run typecheck` и `npm run test:changed` зелёные.
- **AC6.** Отчёт по другим разделам: список экранов с той же схемой и измеренная системная причина в CSS с планом —
  в `evidence.md`.
