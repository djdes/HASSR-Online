## Решения по ходу (спорное — по духу spec)

1. **deploy.yml** — прошлый агент добавил в деплой шаг
   `npx tsx scripts/backfill-area-building.ts --apply`. В spec этого нет, а
   процесс деплоя меняем только с согласия владельца — файл возвращён к HEAD.
   Предложение: запустить backfill на проде вручную после выкладки (см. отчёт).
2. **`prisma/seed-mirror-rooms-to-areas.ts`** (идёт на каждом деплое) — новый
   цех-зеркало получает точку, если помещение с таким названием есть ровно в
   одной точке; иначе — как раньше, без точки. Иначе каждый деплой плодил бы
   цеха «без точки». Проверено: `raw/lib-smoke.txt`.
3. **`demo-organization.ts`** — у демо одна точка, цеха сразу в ней.
4. **Онбординг-шаблон** — цех ищется тем же `pickMirrorArea`, что и у
   помещений (цех этой точки или без точки), а не точным совпадением названия
   по всей организации — иначе «Кухня» второй точки считалась бы уже заведённой.
5. **`room-directory-picker-dialog.tsx`** (окно выбора помещения в журнале
   уборки) тоже берёт виды из `room-kinds.ts`: `guessRoomKind` теперь
   возвращает `production`, и без этого там была бы подпись-код `production`.
6. `POST /api/areas` без `buildingId` при ≥ 2 точках — цех без точки (spec
   задаёт умолчание только для одной точки; угадывать не стали).
7. Окно цеха показывает выбор точки и при одной точке, если у цеха точки нет —
   иначе цех «без точки» туда не перенести.
8. Выбранная точка в шапке: при включённых «журналах по точкам» и ≥ 2 точках
   точка активна всегда (`resolveActiveBuilding` берёт первую доступную), поэтому
   вид «все точки сразу» бывает только с выключенным флагом. Это прежнее
   поведение шапки; Playwright снимал оба режима.
9. Синхронизация фритюра трогает только активные документы; закрытые
   предъявляются как есть. Тип «Фритюрница» — код `fryer` и старое слово
   «фритюрница».

## Окружение (важно для сведения веток)

- **`node_modules` этого worktree жёстко связан (hard links) с `D:/wt/sections-menu`.**
  `prisma generate` пишет файлы клиента; если писать поверх общих inode, клиент
  чужой ветки получил бы `Area.buildingId` (и SQL-ошибки на её базе). Перед
  генерацией `node_modules/.prisma/client` был отсоединён (переименован, затем
  создан заново генерацией); проверено, что у `sections-menu` клиент прежний.
- **Dev-сервер не стартует штатно:** `@swc/core`, вложенный в `next-intl`,
  отказывается от кеша нативного модуля, потому что профиль `C:\Users\Two`
  даёт `BSQL\Yaroslav` полный доступ (SWC требует каталог без прав других
  пользователей у предков). Для проверки использован локальный shim
  (`NODE_OPTIONS=--require …/swc-shim.cjs` в scratchpad, не в репозитории):
  подменяет `@swc/core` только для `next-intl`, где он нужен лишь для
  `useExtracted` (в проекте не включено). В репозиторий ничего не добавлено.
- Playwright 1.59.1 ждёт браузер ревизии 1217, установлен 1243 — запуск с
  `PW_CHROMIUM=…/chromium_headless_shell-1243/…` (без скачивания: на C: ~4 ГБ).
- Scratchpad общий с соседними агентами — один лог dev-сервера был перезаписан
  чужим; дальше все рабочие файлы — в отдельной подпапке.
