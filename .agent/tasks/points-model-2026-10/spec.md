# points-model-2026-10 — модель данных «Торговые точки»

Источник: план `C:\Users\Oleg\.claude\plans\serialized-moseying-conway.md`, раздел 4.3
«Торговые точки» (модель данных) и «Что в коде сейчас» раздела 4. Решения приняты
владельцем; вопросы не задаём, спорное решаем по духу плана и пишем в evidence.

Цель: схема «точка (`Building`) → помещения (`Room` / цех `Area`) → оборудование
(`Equipment`)». Без новых страниц и без правок навигации (`src/lib/app-nav.ts`,
`src/components/layout/*` не трогаем, новых `page.tsx` нет).

## Критерии приёмки

**AC1. Схема.** `Area.buildingId String?` со связью на `Building`
(`onDelete: SetNull`, удаление точки не удаляет цех и оборудование) и индексом
`@@index([organizationId, buildingId])`. `prisma validate` проходит, `db push` на
копии демо-базы (`wesetup_points`) применяется без потери данных.

**AC2. Однократный идемпотентный скрипт заполнения** `scripts/backfill-area-building.ts`.
Правило — по существующей синхронизации `Room` ↔ `Area` по названию
(`normalizePlaceName`: регистр, ё→е, пробелы):
- цех без точки, у которого ровно одна точка с помещением того же названия, → эта точка;
- помещения с таким названием в нескольких точках → цех не трогаем (неоднозначно);
- у организации ровно одна точка → все её цеха без точки уходят в неё;
- уже заполненный `buildingId` не меняется. Повторный запуск ничего не меняет.
По умолчанию — сухой прогон (план в консоль), запись — с `--apply`. Логика плана —
чистая функция с тестами. Скрипт прогнан на копии базы, вывод в evidence.

**AC3. Заполнение при создании и переименовании.**
- `POST /api/settings/rooms`: зеркальный цех создаётся/подхватывается с `buildingId`
  точки помещения; цех без точки с тем же названием получает точку; одноимённые
  помещения в разных точках получают разные цеха.
- `PATCH /api/settings/rooms/[id]` (переименование): переименовывается цех этой
  точки (или без точки) и получает `buildingId`; одноимённый цех другой точки не трогается.
- `DELETE /api/settings/rooms/[id]`: удаляется только зеркальный цех этой точки
  (или без точки), если к нему ничего не привязано.
- `POST /api/areas` и `PUT /api/areas/[id]` принимают необязательный `buildingId`
  (только точка этой организации, иначе 400); без него при одной точке — она.
- `ensureDefaultArea` и онбординг-шаблон ставят точку, когда она одна.

**AC4. Вид помещения «Основное производство».** Значение `production` в общем
модуле видов (`src/lib/room-kinds.ts`) с подписями RU/EN/UZ; zod-схемы API
помещений, окно помещения (`room-editor-dialog.tsx`) и список на
`/settings/buildings` берут виды оттуда. `guessRoomKind("Основное производство")`
→ `production`.

**AC5. `/settings/areas` по точкам.** Цеха сгруппированы по точкам (порядок —
`sortOrder`, имя), блок «Без точки» — для цехов без `buildingId`. Если в шапке
выбрана точка (`loadBuildingContext`, кука `wesetup.building`), показываются только
её цеха и цеха без точки. Окно цеха — с выбором точки, когда точек ≥ 2.

**AC6. `/settings/equipment` по точкам.** Оборудование сгруппировано по точке
своего цеха, с тем же учётом выбранной точки. Окно «Добавить оборудование»: выбор
точки (по умолчанию — выбранная в шапке) и помещения этой точки. Помещение без
зеркального цеха тоже доступно: сервер создаёт цех с этой точкой (`roomId`).
Чужие `areaId`/`roomId` → ошибка 4xx.

**AC7. Фритюрница из «Оборудования» в журнале фритюра.**
- Конфиг `fryer_oil` хранит связи `equipmentLinks: [{ sourceEquipmentId, name }]`,
  строка журнала — `sourceEquipmentId` фритюрницы.
- Чистая функция синхронизации: фритюрница справочника (тип `fryer`) появляется
  в списке оборудования документа; переименование в справочнике доходит до списка;
  неиспользованные образцы «Фритюрница №1–3» убираются, когда есть настоящие фритюрницы.
- Синхронизация запускается при создании документа, при создании/изменении/удалении
  фритюрницы и при открытии документа и наклейки. Учитывается точка: фритюрница
  точки A не попадает в документ точки B; документы без точки получают все.
- В окне «Списки» журнала связанные позиции помечены «из „Оборудования“».

**AC8. QR-наклейка фритюрницы ведёт в форму фритюра.** `/equipment-fill/[id]` для
типа `fryer` показывает форму журнала фритюрных жиров (жир, продукция, оценка;
вторым сканом — окончание жарки), а не форму температуры. Цель записи решает
`equipment-fill-targets.ts`; запись ложится в активный документ фритюра со
строкой этой фритюрницы за сегодня. Нет документа — понятная плашка до ввода и 409
в API. Сотрудник/PIN/«кто заполняет» — по тем же правилам, что у наклеек оборудования.
Тексты формы — RU/EN/UZ.

**AC9. Тесты.** `node --test` на: план заполнения `buildingId` (AC2), выбор
зеркального цеха (AC3), группировку по точкам (AC5/6), виды помещений (AC4),
синхронизацию фритюра и выбор строки QR (AC7/8). Все тесты затронутых модулей зелёные.

**AC10. Проверки.** `npx tsc --noEmit --skipLibCheck` и `npm run lint` по изменённым
файлам без новых ошибок; Playwright на копии базы: `/settings/areas` и
`/settings/equipment` на 1440×900 и 390×800 без горизонтальной прокрутки страницы,
скриншоты в `raw/`. Коммиты в ветке `feat/points-model`, без пуша.
