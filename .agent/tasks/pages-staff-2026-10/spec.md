## Меню раздела после задачи
- «Справочники» (`directories`): **Должности** `/settings/positions` → Сотрудники `/settings/users` → **Доступ и права** `/settings/access`.
- Новая группа «Группы и комиссии» (`groups`): **Бракеражная комиссия** `/settings/brakerage-commission`, **Группа ХАССП** `/settings/haccp-group`, **Контроль-группа** `/settings/control-group`, **Проверяющие и аудиторы** `/settings/inspectors`.
- «Ещё» — без изменений.
- Пункт «Доступ и права» — одна страница без вкладок; прежние четыре страницы (`/settings/permissions`, `/settings/role-presets`, `/settings/journal-access`, `/settings/journals-by-position`) остаются подробными редакторами: в `match` пункта (подсвечивают его, над ними «‹ Доступ и права»), ссылки на них — из блоков страницы с теми же правами, что у страниц. `/settings/position-staff-visibility` — по-прежнему пункт «Ещё».

## Критерии приёмки

### AC1. Должности `/settings/positions`
1. Guard страницы — `hasFullWorkspaceAccess(`; пункт `access: FULL_ACCESS`. Менять (создать, править, удалить, порядок) — тем, кому разрешает API (`/api/positions*`); остальным — просмотр без кнопок.
2. Должности сгруппированы по категориям (руководство / сотрудники / комиссия) в нумерованных карточках; в строке — название, штатная численность, пилюля «занято N из M» (цвет по вакансии/перебору как на `/settings/users`), сколько человек.
3. Сверху итог по организации (`totals`): план, занято, вакансии — одной строкой-пилюлями.
4. Создание и правка — окном (название, категория, «Штатная численность» 0…999 или пусто); удаление — `ConfirmDialog` с последствиями (у должности есть люди → объяснение, что будет); ошибки API показываются тостом.
5. Порядок — кнопками «выше/ниже» (или перетаскиванием) внутри категории → `PUT /api/positions/order`; после перезагрузки порядок тот же.
6. `PageGuide`: что такое штатная численность и «занято N из M».

### AC2. Доступ и права `/settings/access` — одна страница вместо четырёх
1. Guard — `hasFullWorkspaceAccess(`; пункт `access: FULL_ACCESS`, без вкладок; `match`: четыре прежние страницы.
2. Блок «Наборы прав»: каждый пресет (в т. ч. «Контроль-группа») — описание и список возможностей; кто его получает по должности/роли; ссылка «Настроить наборы» на `/settings/role-presets` — только при `admin.full`.
3. Блок «Набор прав у сотрудника»: список людей (ФИО, должность, действующий набор, пометка «по должности» / «назначен вручную»); «Изменить» открывает выбор набора (переиспользовать `staff-preset-picker.tsx`) → `POST /api/staff/[id]/preset`; себе «без администратора» нельзя (сообщение `SELF_LOCKOUT`). Без `admin.full` — только просмотр.
4. Блок «Какие разделы видит»: для каждого набора и для выбранного человека — иконки девяти разделов меню, видимые и скрытые; считается той же функцией, что строит меню (`visibleNav`), без новой настройки. Подпись: разделы меняются набором прав.
5. Блок «Журналы»: сводка по должностям (сколько журналов доступно) и ссылки «Журналы сотрудников» → `/settings/journal-access`, «Должность × журнал» → `/settings/journals-by-position`.
6. Блок «Видимость коллег»: короткая сводка и ссылка на `/settings/position-staff-visibility`.
7. Блок «Права на настройки» со ссылкой на `/settings/permissions` — только если `sessionHasPermission(session, "settings.permissions")`.
8. Тест «права и иерархия зависят от права settings.permissions» обновлён под новую модель (пункт «Иерархия» по-прежнему `PERMISSIONS_FACT`).

### AC3. Бракеражная комиссия `/settings/brakerage-commission`
1. Guard — `hasFullWorkspaceAccess(`. Две карточки: «Бракераж готовой продукции» (`finished_product`) и «Бракераж скоропортящейся продукции» (`perishable_rejection`).
2. В карточке — состав (ФИО, роль в комиссии, должность) из `GET /api/settings/brakerage-commission/<code>`, пустое состояние с подсказкой; кнопка «Изменить состав» открывает существующее окно `commission-dialog.tsx`; после сохранения состав на странице обновлён.
3. Ссылка «Открыть журнал» на журнал; если журнал выключен — пометка и ссылка на включение.
4. Подсказка: состав копируется в действующие документы журнала (как делает API).

### AC4. Группа ХАССП `/settings/haccp-group`
1. Guard — `hasFullWorkspaceAccess(`. Состав и роли — из `PpkRecord` block="team" (та же выборка, что `/production-control/haccp/team`), только чтение.
2. Кнопка «Изменить в программе производственного контроля» → `/production-control/haccp/team`; пустое состояние ведёт туда же.

### AC5. Контроль-группа `/settings/control-group`
1. Guard — `hasFullWorkspaceAccess(`. Список из `GET /api/staff/control-group`: ФИО, должность, кого видит и что назначает (`scope`), ссылка на «Иерархию» для сужения видимости.
2. «Добавить» (при `canManage`) — групповой выбор человека из `candidates` → `POST /api/staff/[id]/preset { preset: "control_group" }`; «Убрать из группы» — `ConfirmDialog` → набор по должности. Ошибки API — тостом.
3. Объяснение: контроль-группа видит всё, подтверждает, назначает задачи, сама не заполняет.

### AC6. Проверяющие и аудиторы `/settings/inspectors`
1. Guard — `hasFullWorkspaceAccess(`. Данные — `GET /api/staff/inspectors-auditors` (или та же функция на сервере).
2. Карточка «Внешние»: доступы портала (вид, метка, срок, статус, кто выпустил, открытия, визиты), кнопка «Выдать QR проверяющему» → `/settings/inspector-portal`.
3. Карточка «Внутренние»: люди и их роли (проверяющий журнала, документа, помещения, аудитор), ссылки туда, где роль меняется.
