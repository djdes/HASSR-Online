# Spec (frozen 2026-09-29): ROOT «Рассылка» — пользователи и загруженные контакты, письмо / колокольчик / push / Telegram

Задача владельца:
- «В админке ROOT сделать раздел: рассылка, там список наших пользователей и через сайт отправка выбранным — произвольный
  текст пользователю + пуш в телефон (приложение) + на почту, опционально».
- «Сделать выбор в рассылке КП с переменными и связью с промокодами, чтобы вставлялись промокоды, сроки и т. д. Выбрал
  кого-то — можно отправить ему КП персональное по его сфере».
- «В будущем хочу загрузить много почт для рассылок из кафе и т. д. и долбить их предложениями прямо из админки».

Ветка `feat/mailing-2026-09-29`, рабочая копия `d:/wt/mailing`, порт 3193. Соседи делают КП (`src/lib/proposal`) и
персональные промокоды (`src/lib/promo/personal-codes.ts`). Их код в этой ветке не появится. Тип «КП» подключит
оркестратор после слияния — здесь сделать для него точку расширения (п. 4).

Что уже есть:
- почта `src/lib/email.ts` (`sendRawEmail`, `renderEmailLayout`, nodemailer через SMTP; на проде локальный relay,
  `noreply@wesetup.ru`);
- колокольчик `src/lib/notifications.ts`;
- веб-push `src/lib/web-push.ts`, push в приложение `src/lib/mobile-push.ts`. Firebase-ключа на проде пока нет, устройств
  в приложении 0 — показывать честно;
- Telegram-бот (найти функции отправки личного сообщения пользователю);
- сферы `ORG_SPHERES`, состояние тарифа `src/lib/billing-period.ts` / `billing.server.ts`, аудит как в соседних
  ROOT-разделах;
- cron-маршруты `/api/cron/*` с `checkCronSecret`.

## Сделать
1. **Схема:**
   - `MarketingContact` — загруженные внешние контакты:
     - email (уникальный, нижний регистр), имя?, компания?, сфера?, город?, телефон?, теги (String[]);
     - обязательные: источник (например «выгрузка 2ГИС 29.09») и основание («согласие на сайте», «деловая переписка»…);
     - статус active | unsubscribed | bounced | complained; lastSentAt?; заметка?
   - `EmailSuppression` — стоп-лист для рекламных писем, общий для пользователей и контактов: email @unique, причина
     unsubscribed | bounced | complained | manual, источник (id рассылки?), createdAt.
   - `User.marketingOptOut Boolean @default(false)`.
   - `MailingCampaign`:
     - название, `kind`, каналы (Json: email / inApp / push / telegram), payload Json;
     - снимок фильтров аудитории;
     - статус draft | scheduled | sending | done | cancelled; scheduledAt?;
     - кто создал, счётчики, даты.
   - `MailingRecipient`:
     - кампания, userId?, contactId?, email?, имя, компания, сфера, organizationId?;
     - статусы по каналам (queued | sent | failed | skipped + ошибка), token (отписка и клики);
     - sentAt, clickedAt, attempts; payload? (персональные данные шаблона, например промокод).
2. **Аудитория (ROOT `/root/mailing`, вкладки).**
   - **«Пользователи».** Активные пользователи; по умолчанию руководители — кто может открыть тариф/настройки.
     - Фильтры: роль (руководители / все), сфера организации, состояние тарифа (бесплатный / бесплатный период /
       подписка / ждёт решения), поиск по организации/имени/почте, «есть почта / Telegram / устройство для push»,
       дата регистрации.
     - Счётчик, таблица с чекбоксами, «выбрать всех найденных».
   - **«Контакты».** Загрузка CSV (разделитель `;` или `,`, UTF-8 и Windows-1251) или вставка текстом.
     - Колонки: email, имя, компания, сфера (название или код), город, телефон, теги.
     - Предпросмотр с сопоставлением колонок и проверкой почты.
     - Дубли и адреса из стоп-листа — отдельной строкой в итоге.
     - Для партии обязательны «Источник» и «Основание».
     - Таблица с фильтрами (сфера, тег, статус, источник), чекбоксы, правка и удаление.
   - **Над загрузкой — короткое честное предупреждение:** «Реклама по email — только с согласия получателя (38-ФЗ «О рекламе»,
     ст. 18). Указывайте, откуда адрес и на каком основании».
3. **Составление.**
   - Тип «Сообщение»: тема/заголовок, текст (абзацы, ссылки, **жирный**), необязательная кнопка (текст + ссылка).
   - Переменные `{имя}`, `{компания}`, `{сфера}` с запасным значением, если пусто.
   - **Каналы — галочки:**
     - «Почта» — пользователи и контакты;
     - «Колокольчик» — только пользователи;
     - «Push» — веб-push + приложение, только пользователи. Показать, у скольких выбранных есть подписки/устройства; Firebase не настроен — так и написать;
     - «Telegram» — пользователи с привязанным ботом.
     
     Для каждого канала — сколько получателей реально дойдёт.
   - Предпросмотр для выбранного получателя.
   - «Тестовая отправка мне» — во все выбранные каналы текущему ROOT.
   - «Отправить сейчас» или «Запланировать» (дата и время по Москве).
   - Черновики сохраняются.
4. **Точка расширения для шаблонов** — `src/lib/mailing/templates.ts`:
   ```ts
   export type MailingRecipientContext = {
     recipientId: string; email: string | null; name: string | null; companyName: string | null;
     sphere: OrgSphere | null; userId: string | null; organizationId: string | null; contactId: string | null;
     unsubscribeUrl: string; trackUrl: (url: string) => string; personal: Record<string, unknown>;
   };
   export type RenderedMailing = {
     email?: { subject: string; preheader?: string; html: string; text: string; attachments?: EmailAttachment[] };
     inApp?: { title: string; body: string; url?: string | null };
     push?: { title: string; body: string; url?: string | null };
     telegram?: { text: string; url?: string | null };
   };
   export type MailingTemplate<P = unknown> = {
     kind: string; label: string;
     /** Перед отправкой: например, создать персональные промокоды и сложить их в recipient.payload. */
     prepare?(campaign: { id: string; payload: P }, recipients: Array<{ id: string; email: string | null; organizationId: string | null; companyName: string | null; sphere: OrgSphere | null }>): Promise<Record<string, Record<string, unknown>>>;
     render(payload: P, ctx: MailingRecipientContext): Promise<RenderedMailing>;
   };
   export function registerMailingTemplate(t: MailingTemplate<any>): void;
   export function mailingTemplates(): MailingTemplate<any>[];
   ```
   - Тип «Сообщение» реализовать через этот же интерфейс.
   - Форма составления: общие поля — здесь; поля конкретного типа — отдельный компонент по `kind`, чтобы оркестратор
     добавил «КП» (сфера по получателю, промокод: нет / выбрать / персональные с %, «навсегда», сроком; вложить PDF)
     одним файлом и строкой регистрации.
5. **Отправка.**
   - Очередь — строки `MailingRecipient`. Разбирает cron `/api/cron/mailing` (CRON_SECRET, раз в минуту) + толчок сразу
     после запуска.
   - Идемпотентно: канал получателя отправляется один раз. Временные сбои — до 3 попыток.
   - Отмена кампании останавливает неотправленное.
   - **Ограничение скорости** писем — настройка `PlatformSetting` `mailing.settings`: писем в минуту (по умолчанию 20),
     в сутки (по умолчанию 300). В ROOT видно, сколько отправлено сегодня.
   - **Отдельный отправитель рекламных писем:** env `MARKETING_SMTP_HOST/PORT/USER/PASSWORD/SECURE`, `MARKETING_FROM`.
     - Не задан — идёт через основной SMTP.
     - В ROOT тогда жёлтое предупреждение: «Рекламные письма уходят с noreply@wesetup.ru — если их пометят спамом,
       служебные письма (коды входа, счета) тоже начнут попадать в спам. Лучше отдельный адрес/домен».
   - **В каждом рекламном письме:**
     - ссылка «Отписаться» (`/unsubscribe/<token>`);
     - заголовки `List-Unsubscribe` (https + mailto) и `List-Unsubscribe-Post: List-Unsubscribe=One-Click`;
     - адресаты из стоп-листа и с `marketingOptOut` — `skipped`.
   - **Пустой SMTP (рабочая копия):** режим сухой отправки — письма пишутся файлами `.html`/`.eml` в
     `MAILING_DRY_RUN_DIR`, если задан. Иначе — только лог.
   - Колокольчик — `upsertNotification`. Push — существующие фоновые отправители. Telegram — существующая отправка ботом.
   - Логи: `[mailing] campaign=… status …`, по получателю — trace/ошибки. Аудит — запуск, отмена, загрузка контактов.
6. **Отписка и клики.**
   - `/unsubscribe/[token]` — страница с одной кнопкой «Отписаться» (и POST one-click без страницы).
     - Пишет стоп-лист и статус контакта / `marketingOptOut` пользователя.
     - Служебные письма не трогает.
     - Вернуть подписку — в профиле пользователя, переключатель «Новости и предложения на почту»: найти место в
       настройках уведомлений.
   - Клики: ссылки письма → `/r/<token>/<n>`. Адрес берётся из сохранённого payload кампании, НЕ из параметра — иначе
     открытый редирект. Пишет `clickedAt`, ведёт по адресу.
7. **История:**
   - список кампаний: название, тип, каналы, счётчики (в очереди / отправлено / ошибка / пропущено / клики), статус;
   - карточка кампании: получатели с статусами и ошибками, «Отменить», «Повторить неудачные»;
   - «Стоп-лист»: поиск, добавить/убрать адрес вручную (с аудитом).
8. Ссылка на раздел — в меню ROOT.

## Проверка
- **Юнит:**
  - разбор CSV (кодировки, разделители, дубли, плохие адреса);
  - фильтры аудитории;
  - подстановка переменных с запасными значениями;
  - подпись токенов, ограничение скорости и суточный лимит;
  - стоп-лист и `marketingOptOut` → skipped;
  - идемпотентность и повторы;
  - редирект только по сохранённым ссылкам.
- **E2E** (390 и 1280), сухая отправка в папку, скриншоты:
  - загрузка контактов вставкой;
  - выбор пользователей по фильтру;
  - сообщение во все каналы;
  - тест себе;
  - запуск → cron разобрал очередь с ограничением скорости → статусы;
  - письмо в папке с отпиской и заголовками;
  - отписка → повторная рассылка пропускает адрес;
  - клик → `clickedAt`;
  - отмена кампании.
- `npm run typecheck`, `npm test`.

## Критерии приёмки
- AC1: ROOT выбирает пользователей (фильтры) и загруженные контакты, отправляет текст в почту / колокольчик / push /
  Telegram по галочкам, с тестом себе и планированием.
- AC2: очередь с ограничением скорости, стоп-лист, отписка (ссылка + заголовки), клики, история и повторы — всё в логах
  и аудите.
- AC3: точка расширения шаблонов по интерфейсу выше; «Сообщение» сделано через неё.
- AC4: честные предупреждения про 38-ФЗ и отдельный адрес отправки; реальных писем из рабочей копии не уходит.
