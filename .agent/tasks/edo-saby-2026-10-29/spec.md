# ЭДО из ROOT: отправка договоров, счетов и УПД клиентам через Saby (СБИС)

Задача владельца (дословно): «Сделай так же возможность отправки документов в ЭДО по ИНН
определение, реализация есть вот тут C:\www\DocsFlow, отправлять будем договора, УПД, счета
одним кликом.»

Отправитель — всегда ООО «БФС» (оператор wesetup.ru, реквизиты — `readPlatformRequisites()`),
получатель — организация-клиент WeSetup (`Organization`), определяется по её ИНН (+КПП, у ИП —
ФИО). Источник реализации — DocsFlow (`src/lib/edo/saby/*`, `send-core.ts`, `send-service.ts`),
переносится с адаптацией, тесты — на `node:test`.

## Ограничения (заморожены)

- Saby не умеет отложенную подпись через API (живой опыт DocsFlow 23.10.2026): сайт только
  ЗАПИСЫВАЕТ документ черновиком (`СБИС.ЗаписатьДокумент`), подписывает КЭП и отправляет человек в
  Saby по ссылке `СсылкаДляНашаОрганизация`.
- Вход только по ключам приложения (`/oauth/service/`), сессия кэшируется (≤5 сессий на
  приложение), выход при смене ключей/отключении.
- Защищённый ключ и сессия — только в БД, AES-256-GCM, ключ = sha256("saby:" + NEXTAUTH_SECRET);
  наружу (API/HTML) не отдаются никогда.
- Адрес Saby — только из белого списка (`online.saby.ru`, `online.sbis.ru`, тест `fix-online.sbis.ru`);
  `http://127.0.0.1:<порт>` / `http://localhost:<порт>` — только при `NODE_ENV !== "production"`
  (локальная заглушка для e2e).
- Схема — только добавления (новые модели + обратная связь у `Organization`).
- Не трогать `src/app/root/organizations/[id]/page.tsx`, `src/lib/whats-new-notes.ts`,
  `.github/workflows/deploy.yml`. Без пушей и PR.
- Живой Saby в тестах не вызывается.

## Критерии приёмки

- **AC1. Клиент Saby перенесён.** `src/lib/edo/saby/{rpc,session,orgs,edo-api,status}.ts`:
  транспорт JSON-RPC с разбором ошибок, вход/выход по ключам, кэш сессии с одним повторным входом
  на 401 и single-flight, белый список адресов, наши организации (`СБИС.СписокНашихОрганизаций`),
  описание стороны (ООО по ИНН+КПП+названию, ИП по ИНН+ФИО), запись черновика с нашим GUID,
  чтение состояния (`Удален: Да` = нет документа), коды состояний и подписи статусов как в DocsFlow.
  Unit-тесты на `node:test` с подделкой fetch / вызывателя.
- **AC2. Схема.** `EdoCabinet` (один кабинет на платформу: clientId, appSecretEnc, sessionEnc,
  baseUrl, orgs Json, status, checkedAt, lastError, createdByUserId, даты) и `EdoDocument`
  (organizationId + связь, kind contract|invoice|upd|other, sourceId?, sabyType, number, docDate,
  fileName, sabyDocId — наш GUID, сохраняется ДО записи, cabinetClientId, реквизиты получателя,
  результат проверки получателя, stateCode Int?, stateName, signUrl, error, deletedAt,
  sentByUserId, createdAt/updatedAt/refreshedAt). `prisma validate` + `db push` на локальной БД.
- **AC3. Определение по ИНН.** `checkCounterpartyEdo({inn,kpp,…})` через
  `СБИС.ИнформацияОКонтрагенте` (`{"Участник": {СвЮЛ|СвФЛ, "ДопПоля": "СписокИдентификаторов"}}`)
  → «подключён к ЭДО: Saby», «через роуминг: <оператор>», «не найден / нет идентификатора —
  Saby отправит приглашение». Получатель определяется автоматически из ИНН/КПП/ФИО клиента;
  ID участника вручную — необязательное переопределение. Результат виден в UI до отправки.
- **AC4. Отправка.** `sendToEdo({organizationId, kind, sourceId?, file?, number?, date?,
  participantId?, sentByUserId})` с реестром источников: `invoice` → PDF `renderInvoice` как
  `СчетИсх`; `upd` → PDF УПД (`ensureClosingDocument` + `renderPdf`) как `ДокОтгрИсх`;
  `contract` → подключаемый источник (заглушка с понятной ошибкой «не подключён») + ручной файл
  как `ДоговорДок`; `other` → ручной файл. Проверка принадлежности источника организации.
  Защита от дублей: живой документ того же источника (или той же организации+вида+номера+даты для
  ручного файла) не создаёт второй черновик — черновик (0) перезаписывается тем же GUID после
  перечитывания, отправленный → 409; удалённый/отклонённый/аннулированный/ошибка доставки — не
  мешает. Сбой записи — перечитывание по GUID (ответ мог потеряться). `refreshEdoDocuments()`
  перечитывает неокончательные документы ≤90 дней, не больше N за вызов.
- **AC5. API.** `src/app/api/root/edo/**`: кабинет (GET/PUT/POST проверить/DELETE), организации-
  клиенты (поиск по названию/ИНН), источники клиента (счета/УПД), проверка получателя, отправка
  (JSON и multipart ≤10 МБ, pdf/docx/odt/rtf), история, обновление статусов. Каждый —
  `requireRoot()`, zod; секреты в ответах отсутствуют.
- **AC6. ROOT UI.** `/root/edo`: подключение кабинета (ID подключения, защищённый ключ — очищается
  после сохранения, выбор контура), «Проверить подключение», «Отключить» (`ConfirmDialog`), наши
  организации из Saby с флагом ЭДО и подсветкой ООО «БФС» (предупреждение, если нет/неоднозначно);
  форма «Отправить документ» (поиск клиента, вид, номер/дата, файл для договора/прочего, выбор
  счёта/УПД клиента), результат проверки получателя, явная подсказка «Откройте Saby и нажмите
  «Подписать и отправить»»; история со статус-чипами, ссылкой «Подписать в Saby», «Обновить
  статусы». Пункт «ЭДО» в навигации ROOT (группа «Деньги и продажи», ru/en/uz). Тексты — i18n
  (`rootEdo`, ru/en/uz). Переиспользуемая кнопка `src/components/root/edo-send-button.tsx`
  (`{organizationId, kind, sourceId, label?}`), недоступна с пояснением без кабинета.
- **AC7. Проверки.** `npm run typecheck`, `npx eslint` по изменённым файлам, unit-тесты ЭДО,
  `npm run i18n:check`, `npm run test:gate` — зелёные. E2E (Playwright) против локальной заглушки
  Saby: подключение → наши организации → отправка договора файлом клиенту → в истории «Ждёт
  подписи в Saby» со ссылкой → «Обновить статусы» меняет статус. Скрипты — в `raw/`.

## Вне объёма

- Формализованный XML УПД 5.03 (генератор DocsFlow не проходил ФЛК Saby; решение и компромисс —
  в evidence).
- Серверная подпись, цепочки «счёт → УПД», входящие документы, вебхуки (у Saby их нет).
- Размещение кнопки на карточке организации (делает ведущий).
