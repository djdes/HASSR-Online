# Договор оказания услуг из ROOT-карточки организации — спецификация (заморожена 2026-10-29)

## Запрос владельца

«При переходе в пользователя сделать отправку договора заполненную от БФС + самого
пользователя данные ИНН что он ввёл, чтобы всё было заполнено… Шаблон договора
придумай сам на оказание услуг стандартный, в котором БФС т.е. наш сайт был бы выгоден.»

«Пользователь» — организация-клиент в ROOT (`/root/organizations/[id]`). Реквизиты
БФС — из `PlatformSetting` `legal.requisites` (`readPlatformRequisites()`), клиента —
из `Organization` (+ снимок ЕГРЮЛ) через `buildDocumentOrgBlock`.

Дополнение лида (тот же день): фирменный стиль документов по образцам
`WeSetup - КП и счета (новый дизайн)` — тёмные скруглённые карточки шапки и подвала
на каждом листе, градиентный «сетап», нумерованные заголовки разделов, таблицы с
тёмной строкой заголовка, Manrope. Общий jsPDF-кит `src/lib/brand-docs/` для
договора, позже — КП и счёта.

## Критерии приёмки

- **AC1. Шаблон договора.** `src/lib/contracts/template.ts`, версия
  `CONTRACT_TEMPLATE_VERSION = "2026-10-29"`: стандартный договор оказания услуг
  (ГК РФ гл. 39) на доступ к WeSetup и сопутствующие услуги, выгодный Исполнителю:
  100 % предоплата по счёту, цена — по тарифу на сайте и счетам (сумм в тексте нет),
  изменение тарифов с уведомлением ≥ 10 дней без влияния на оплаченный период,
  приёмка УПД/актом с молчаливым согласием через 5 рабочих дней, приостановка за
  неоплату, ответственность ≤ платы за последний месяц, без упущенной выгоды,
  ответственность Заказчика за данные журналов и штрафы, ИС у Исполнителя (простая
  неисключительная лицензия на срок), ПДн — Заказчик оператор, Исполнитель
  обрабатывает по поручению (ч. 3 ст. 6 152-ФЗ), конфиденциальность, ЭДО (КЭП,
  скан/почта до оригиналов), форс-мажор, срок 1 год с автопролонгацией,
  односторонний отказ Исполнителя при нарушении, претензии 15 рабочих дней,
  Арбитражный суд Московской области, реквизиты и подписи. В коде отмечено:
  нужна проверка юристом.
- **AC2. Заполнение без дыр.** Чистая функция строит текст из снимков сторон и
  параметров: в тексте нет `undefined`/`null`/`{{…}}`/пустых подстановок; ИП (ИНН
  12 цифр или тип INDIVIDUAL) — «индивидуальный предприниматель …, ОГРНИП, действующий
  на основании свидетельства/листа записи ЕГРИП», юрлицо — «в лице <должность> <ФИО>,
  действующего на основании Устава». Недостающее поле клиента — линия для ручного
  заполнения, а не пустота.
- **AC3. Модель данных.** Prisma `ClientContract` (аддитивно): организация,
  уникальный номер `WS-ГГГГ/NNNN` (последовательный в году, выдаётся в транзакции),
  дата, город, версия шаблона, снимки продавца и покупателя, параметры, статус
  issued|sent|voided, sentAt, sentTo[], sentByUserId, createdByUserId, voidedAt.
  Перерисовка — только из снимка.
- **AC4. Рендер.** `renderClientContractPdf(contractId)` в
  `src/lib/contracts/render.server.ts` → `{ fileName, bytes }`: A4, фирменные шапка
  и подвал на каждом листе, нумерованные разделы, «Стр. N из M», реквизиты сторон
  двумя колонками, линии подписей, факсимиле и печать БФС — если загружены и
  включены. `renderClientContractDocx(contractId)` — тот же текст для правки.
- **AC5. Кит фирменных документов.** `src/lib/brand-docs/pdf-kit.ts`: шрифты
  Manrope (DejaVu — запасной), `letterhead`, `footerCard`, `sectionTitle`,
  `dataTable`, `partyRows`, `bankGrid`, `signatureBlock`; продавец передаётся
  параметром (из `readPlatformRequisites()`, без хардкода реквизитов). В репозиторий
  — только нужные маленькие PNG.
- **AC6. API** `src/app/api/root/organizations/[id]/contracts/**`, каждый обработчик
  за `requireRoot()`, вход — zod: предпросмотр (данные + чек-листы + получатели),
  выпуск, PDF, DOCX, отправка письмом, аннулирование. Выпуск/отправка/аннулирование
  — в `AuditLog` через `recordAuditLog`. Аннулированный договор не отправляется.
- **AC7. Письмо.** `sendClientContractEmail({ contractId, to, subject?, message?,
  senderUserId })` в `src/lib/contracts/send.server.ts`: `renderEmailLayout` +
  `sendRawEmail` с PDF во вложении; статус sent/sentAt/sentTo — только если письмо
  принято транспортом; без SMTP API честно отвечает «почта не настроена».
- **AC8. Получатели.** Предлагаются: почта владельца (кроме технической), его
  `contactEmail`, `accountantEmail`, почты из снимка ЕГРЮЛ; без дублей, валидные.
- **AC9. UI.** `src/components/root/client-contract-card.tsx` на странице
  организации (минимальная правка `page.tsx`: импорт + элемент): готовность
  реквизитов БФС (ссылка на `/root/requisites`) и клиента (ИНН, наименование,
  юр. адрес, руководитель; «Обновить из ЕГРЮЛ»), форма (дата, подписант клиента,
  основание, факсимиле), кнопки PDF / DOCX / «Отправить на почту» (чипы адресов,
  тема, сообщение, `ConfirmDialog`), история с повторным скачиванием и
  аннулированием (`ConfirmDialog` danger). Тексты — i18n ru/en/uz, дизайн-система.
- **AC10. Тесты** (`node --test`): заполнение шаблона (нет пустот, ИП/ООО), формат
  номера, выбор получателей, PDF (больше 1 страницы, оба ИНН в тексте).
- **AC11. E2E** (Playwright, локальная БД, ROOT): карточка видна, договор выпускается,
  PDF содержит ИНН БФС и клиента, отправка без SMTP даёт понятный ответ. Скрипты —
  `.agent/tasks/client-contract-2026-10-29/raw/`.
- **AC12. Проверки.** `npm run typecheck`, eslint изменённых файлов, `npm run
  i18n:check`, unit-тесты, `npm run test:gate` — без новых падений.
