Задача: настроить в этом репозитории выкатку на прод ТОЛЬКО через главную ветку (`main` или `master` — определи сам по `git remote show origin`), с проверками перед деплоем, мерджем через PR и автоматическим деплоем на каждый пуш в главную ветку, с ожиданием сервера, проверкой после рестарта и автоматическим откатом. Образец — репозиторий djdes/HASSR-Online: `.github/workflows/deploy.yml`, `scripts/wait-for-port.sh`, `scripts/post-deploy-check.sh`, `scripts/deploy-rollback.sh`, `scripts/deploy.sh`, тест `src/lib/deploy-scripts.test.ts`, `src/app/api/build-info` и `src/app/api/health`, `.husky/`, AGENTS.md → «Production deploy rules», «Conventions for AI agents». Если есть доступ — прочитай их и повтори устройство, а не только идею.

## 0. Сначала разберись, ничего не ломая
- Главная ветка, стек, команды проверок (lint, typecheck, тесты, сборка), есть ли уже CI и как прод выкатывается СЕЙЧАС: сервер по SSH (PM2/systemd/docker) или платформа (Vercel/Netlify/Render/Fly). Есть ли БД и миграции, какие секреты уже есть в Actions (только имена, значения не выводи).
- Работающий прод не трогай. Заморозь план с критериями приёмки (AC1, AC2, …) в `.agent/tasks/<id>/spec.md` и только потом меняй.
- Если чего-то не хватает (адрес сервера, имена секретов, URL прода) — спроси владельца одним списком, остальное делай сам.

## 1. Workflow деплоя `.github/workflows/deploy.yml`
- Запуск: `push` в главную ветку + `workflow_dispatch` (ручной передеплой).
- Job `reject-non-<main>`: если `github.ref` — не главная ветка, падает с понятной ошибкой и ничего не выкатывает. Остальные jobs — `if: github.ref == 'refs/heads/<main>'`.
- `concurrency`: одна группа `production-deploy`, `cancel-in-progress: false` (активный деплой не убивается, новый ждёт). В очередь прода встаёт только главная ветка.
- Gate — параллельные jobs: typecheck/lint и тесты (долгие тесты — шардами). Сборка/упаковка архива идёт параллельно с gate; сервер трогаем только после зелёного gate (`needs: [gate, upload]`).
- Защита от отката: перед деплоем спроси прод, какой коммит он обслуживает (эндпоинт версии, п. 2), и сравни с `GITHUB_SHA` через `gh api repos/$REPO/compare/<served>...<sha>`. Если наш коммит старше того, что на проде, и тот уже в главной ветке — откажись (это Re-run старого прогона). Прод не ответил — предупреждение, не блок.
- SSH (если деплой на свой сервер): креды только в секретах Actions (`DEPLOY_SSH_HOST/USER/PORT` + ключ или пароль).
  - Перед первым SSH-шагом каждого job — `scripts/wait-for-port.sh <host> <port>`: TCP-проба (`timeout 10 bash -c "exec 3<>/dev/tcp/$HOST/$PORT"`) до 8 раз с паузой 15 с; не дождались — понятная ошибка «SSH-порт сервера не отвечает из GitHub Actions». Хост в лог не печатать. В job без checkout — `actions/checkout` с `sparse-checkout: scripts`.
  - Повторять только идемпотентные шаги (`mkdir -p`, SCP архива): шаг с `id` и `continue-on-error: true`, затем `if: steps.<id>.outcome == 'failure'` — пауза + снова wait-for-port, затем тот же шаг ещё раз. Таймаут подключения (`timeout:`) — 60 с.
  - Неидемпотентные шаги (распаковка с удалением архива, миграции, рестарт) не повторять — только ожидание порта перед ними. Длинный деплой — несколько SSH-шагов со своими таймаутами.
- На сервере: распаковка → установка зависимостей (`npm ci` только если менялся lockfile) → сборка в ОТДЕЛЬНЫЙ каталог, пока старая сборка обслуживает сайт → миграции БД → запомнить обслуживаемую версию (`curl /api/build-info`) → атомарная подмена каталогов (старая сборка — в `*-previous`) → рестарт → прогрев ключевых страниц.
- После рестарта — `scripts/post-deploy-check.sh <local_url> <GITHUB_SHA>`: до ~1,5 мин ждёт, пока `/api/build-info` отдаст выкатываемый коммит (первые 7 символов), а `/` и страница входа ответят 2xx/3xx. Не дождался — `scripts/deploy-rollback.sh <local_url> <запомненная версия>`: вернуть `*-previous` (неудачную сборку — в `*-failed` для разбора), вернуть файл версии, перезапустить процесс, проверить прежнюю версию тем же скриптом; деплой падает с понятной причиной. `*-previous` удалять только после успешной проверки.
- Миграции БД: дамп перед изменением схемы. Автоматически применяются только добавляющие изменения (новые таблицы/колонки/индексы). Удаление или смена типа — стоп деплоя, и в лог выводятся конкретные операции (таблица, колонка), а не только «нужен ручной разбор». Никаких `--accept-data-loss`/`--force`. Откат сборки схему не трогает: прежняя сборка работает с добавленными колонками.
- Уведомление о падении (Telegram/Slack/почта — что есть в секретах) с причиной и ссылкой на запуск.
- Платформа вместо сервера (Vercel и т. п.): прод-ветка = главная, автопромоут превью в прод выключен, деплой ждёт зелёных проверок; после выкатки — та же проверка версии, откат — встроенным «rollback» платформы.

## 2. Метки версии и ручной запасной путь
- CI пишет `.build-sha` (полный SHA) и `.build-time` до сборки; версия вшивается в сборку (env при build). `GET /api/build-info` (или `/version`) отдаёт вшитую версию: `buildId` (7 символов), `fullBuildId`, `buildTime`.
- Health-эндпоинт показывает ту же вшитую версию (`buildSha`), а файл `.build-sha` — отдельным полем (`buildShaOnDisk`) и только когда он расходится с работающей сборкой: деплой пишет файл в начале, и при упавшем деплое файл называет версию, которой на сайте нет. Выбор версии — чистая функция с unit-тестом.
- `scripts/deploy.sh` — только на случай недоступности Actions: отказывается работать, если `HEAD != origin/<main>` или в рабочей копии есть незакоммиченное; креды — из локального файла вне git. Подсказка в ошибке: `git worktree add ../<repo>-deploy origin/<main>`.

## 3. Тесты и проверка самого деплоя
- Деплой нельзя прогнать в PR (он запускается только из главной ветки), поэтому до мерджа: `actionlint` по workflow, `bash -n` по каждому `run:`/`script:`-блоку (выражения `${{ … }}` заменить заглушкой), unit-тесты скриптов.
- Тест скриптов (`node:test` или аналог стека): заглушка HTTP-сервера отдаёт версию из файла в временном каталоге, заглушка pm2 (`PM2="bash stub.sh"`) «перезапускает» — копирует файл версии. Случаи: верная версия → 0; чужая версия, 500 на странице входа, сервер не отвечает → 1; откат возвращает прежний каталог и версию и проверяет её; без `*-previous` откат ничего не трогает и падает; порт открыт/закрыт. Скрипты запускать асинхронно (синхронный запуск заблокирует заглушку сервера в том же процессе), прокси из окружения дочернего процесса убрать.

## 4. Локальные хуки
- pre-commit (быстро, секунды): поиск секретов в добавленных строках (токены ботов, `sk-ant-…`, `ghp_…`, `github_pat_…`, пароли в командах) + тесты рядом с изменёнными файлами. pre-push — ничего тяжёлого: полный прогон делает CI.
- Хуки ставятся сами (`prepare`-скрипт или аналог). Обходить `--no-verify` нельзя.

## 5. Правила в AGENTS.md (и короткая ссылка из CLAUDE.md / .cursorrules)
Раздел «Production deploy rules»:
- Прод выполняет только код из `origin/<main>`. Обычный путь — пуш (мердж PR) в главную ветку; передеплой — «Run workflow» с выбранной главной веткой.
- Никогда не деплоить другую ветку, тег, локальную или грязную копию, снапшот релиза; не править код на сервере руками. Ручная выкладка в обход главной ветки ломает следующий деплой (расхождение схемы БД) и затирается им.
- Не делать Re-run старого деплоя: он выкатит старый коммит со старым workflow. Откат — `git revert` в главной ветке.
- Ветки — от свежей главной, удалять после мерджа.

Раздел «Conventions for AI agents»:
- Вся готовая работа уходит в прод через PR в главную ветку, squash-merge. Перед мерджем: `git fetch origin <main>`, влить `origin/<main>` в ветку задачи (без rebase и force-push на общих ветках), конфликты решать инструментами репо (lockfile, сгенерированные файлы — перегенерировать, не руками), заново прогнать проверки, запушить, и только тогда мерджить. Мерджить только зелёный PR без конфликтов; падающий тест не пропускать и не отключать.
- Слова владельца «в прод» = смерджить PR задачи в главную ветку без повторного вопроса; после мерджа — дождаться деплоя и сверить версию на проде (`/api/build-info`).
- В описании PR — что меняет деплой (новые колонки, миграции, переменные окружения).

## 6. Настройки GitHub (сделай, если есть права; иначе — чек-лист владельцу)
- Ruleset/branch protection на главной ветке: только через PR, обязательные проверки = jobs gate, запрет force-push и удаления ветки.
- «Automatically delete head branches» — включить.
- Секреты Actions для деплоя заведены (перечисли имена).
- Приложению Claude на GitHub — права Actions: read & write, чтобы агент мог перезапустить упавший деплой без лишнего коммита.

## 7. Проверка и сдача
- Всё — одним PR. PR не деплоит; деплой стартует только после мерджа.
- Проверь вручную: «Run workflow» на другой ветке падает на reject-job и ничего не выкатывает; первый деплой после мерджа зелёный, в логе видны «порт сервера отвечает» и «[verify] сайт отдаёт <sha>»; `/api/build-info` на проде отдаёт SHA мерджа, `/api/health` — ту же версию без `buildShaOnDisk`.
- Запиши доказательства в `.agent/tasks/<id>/evidence.md` и опиши владельцу: что настроено, что осталось сделать в настройках GitHub, как передеплоить и как откатить.
