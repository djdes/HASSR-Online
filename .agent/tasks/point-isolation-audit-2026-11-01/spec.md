# Полная проверка изоляции: точка ↔ точка, организация ↔ организация (2026-11-01, вторая волна)

Запрос владельца: найти все места, где торговая точка видит, получает или меняет данные другой
точки, а одна организация влияет на другую или видит её данные. Каждую находку перепроверить по
коду и **визуально** (то, что не подтверждено вживую, багом не считается), исправить через PR.
Исключение — мастер-меню и настройки бракеража (настраиваются отдельно). Слияние — только после
«да» владельца.

## Как искали и проверяли

- Шесть параллельных проверок кода (только чтение): кроны и уведомления; кабинет (люди, HR,
  настройки); Mini App, боты, киоск, QR, телефоны, MCP/REST v1, ИИ; документы журналов и записи;
  интеграции и печать; между организациями.
- Динамический сканер `raw/leak-scan.mjs`: все GET-маршруты API и страницы кабинета от лица
  повара и руководителя точки А, руководства с точкой А в шапке, повара точки Б и второй
  организации; ищет метки объектов чужой точки и чужой организации. Прогон на prod-сборке:
  `raw/leak-scan-prod.txt`.
- Живое воспроизведение каждой находки на локальной копии (НЕ прод): база `wesetup_iso`
  (фикстура `raw/fixture*.ts`: офис, точки А и Б, люди, оборудование, документы, CAPA, партии,
  потери, приёмка, этикетки, принтеры, ссылки проверяющего, назначения чек-листов, визит
  проверяющего, вторая организация, партнёр «только просмотр»), `next build` + `next start`.
  Скрипты: `raw/repro.mjs`, `raw/repro2.mjs`, `raw/token-forge.mjs`, `raw/partner-view.mjs`,
  `raw/print-agent-name.mjs`; снимки экрана — `raw/shot.mjs`.

## Критерии приёмки (подтверждённое вживую → исправить)

### AC1. Сессия и общие разделы компании (PR «сессия»)
1. Пользователь не может сам вписать в свой токен `activeOrganizationId` / `partnerAccess`
   (`POST /api/auth/session`); руководитель точки после такой попытки по-прежнему получает 403
   на изменения общих разделов компании (`POST /api/products`). Сервер проверяет запреты
   руководителя точки по свежим точкам сессии, а не только proxy по токену.
2. Руководителю точки закрыто чтение (GET → 403): `/api/settings/organization/export`,
   `/api/settings/rpn-appendix`, `/api/settings/external-token`, `/api/organizations/permissions`,
   `/api/staff/control-group`, `/api/settings/subscription/transition`,
   `/api/settings/master-cabinet`, `/api/settings/badge`, `/api/settings/webhooks/subscriptions`.
   Руководству всей компании — по-прежнему 200.
3. Руководитель точки не меняет общие настройки компании: `PATCH /api/settings/badge`,
   `PATCH /api/settings/journal-controls`, `PUT /api/settings/journals/<code>/distribution`,
   `PUT /api/settings/journals/<code>/bonus` → 403; на `/settings/journals` у него нет людей
   других точек.
4. `POST /api/profile/complete` (анкета компании) — только руководству всей компании; повар
   получает 403, название и ИНН организации не меняются.
5. Партнёр с уровнем «только просмотр» не меняет реквизиты клиента
   (`PATCH /api/partner/clients/<orgId>` → 403).

### AC2. Люди точки (PR «люди»)
1. Руководитель точки не действует над человеком всей компании (офис, без точки, все точки):
   `POST /api/staff/<id>/credentials` для руководителя «офис + точка А» → 403.
2. `/reports/by-user/<человек точки Б>` у руководителя точки А — «не найдено»;
   `GET /api/certificate/staff?userId=<человек точки Б>` → 403/404.
3. `POST /api/verifications/<задача человека точки Б>` у руководителя точки А → 403/404.
4. Руководство с точкой А в шапке: `/bonuses`, `/competencies`, `/team`, `GET /api/team`,
   `/settings/schedule`, `/settings/inspectors` — без людей точки Б; руководитель точки А:
   `/settings/inspectors` и `GET /api/staff/inspectors-auditors` — без людей и ссылок точки Б.
5. Преемник уволенного сотрудника — из точек уволенного (не с другой точки).
6. Уборщиком помещения точки А нельзя назначить человека точки Б.

### AC3. Объекты и записи точки (PR «объекты»)
1. Через журнал холодильников точки А нельзя изменить холодильник точки Б.
2. `room-scopes` документа уборки точки А не принимает помещение точки Б.
3. Потери: подсказки товаров, форма `/losses/new` и `POST /api/losses` — только цеха и записи
   своей точки (у руководства — точки из шапки).
4. Назначения чек-листов: страница, `GET/POST/PATCH/DELETE /api/checklists/assignments*` — только
   своя точка и её люди.
5. Проверки по чек-листам: список и карточка по id — только своей точки.
6. Посещения проверяющих: список и API — только по ссылкам своей точки (и общие).
7. `GET /api/equipment?documentId=…` — документ чужой точки не открывает её оборудование;
   общий документ даёт оборудование видимых человеку точек.

### AC4. QR, печать, «Вся организация» (PR «QR и печать»)
1. «QR-коды» у руководителя точки А — без документов точки Б; `GET /api/qr-fill/journal/<код>:<документ Б>` → 404.
2. QR в шапке печатного журнала точки ведёт к документам этой точки (и общим), а не к выбору
   документов всех точек.
3. Печать общего журнала с точки А создаёт задание точки А (его не печатает принтер точки Б).
4. Подключение принтера на точке А не отзывает одноимённый принтер точки Б.
5. «Сегодня» и «Наборы журналов» в режиме «Вся организация» считают все точки, а не только офис.

### AC4b. Дополнение по ходу работы (запрос владельца 2026-11-01 и живая проверка)
1. Фирменный стиль у каждой организации свой: новая организация «как текущая» получает свою
   копию логотипа (не ссылку на файл донора); смена логотипа и цветов в одной организации не
   меняет другую. Уже созданные организации чинит `scripts/repair-shared-org-logos.ts`
   (по умолчанию только показывает, `--apply` — исправляет).
2. Партнёр в кабинете клиента не получает общий ключ внешнего API клиента
   (`GET /api/settings/external-token` → 403), страница «API» ему ключ не показывает.
