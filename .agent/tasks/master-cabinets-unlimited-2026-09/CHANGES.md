# Мастер-кабинетов сколько угодно (2026-09-30)

Запрос (чат с заказчиком, 30.09): «Где создать ещё один мастер-кабинет? Нужен один на школы, один на сады». Денис: «предусмотреть создание неограниченного числа. У нового аккаунта первый — под строчкой с кабинетом как „Создать мастер кабинет“, и после создания первого снизу ещё одна такая же кнопка».

Было. Мастер-кабинет создавался только из «Настройки → Мастер-кабинет справочников» и один на пул кода справочника: второй в том же пуле не создавался — только приглашение в существующий. Раздел «Кабинет» в меню профиля появлялся, только когда кабинет уже был.

Теперь.
- Меню профиля (компьютер — выпадающий список, телефон — лист, мини-приложение — карточка «Кабинет»): у владельца аккаунта раздел «Кабинет» есть всегда, под строками кабинетов — «Создать мастер-кабинет». После каждого созданного кабинета кнопка остаётся под ним — кабинетов сколько угодно.
- Окно «Новый мастер-кабинет»: название («Школы», «Сады») и галочки объектов аккаунта. Сразу отмечены объекты без кабинета (у нового аккаунта — все). Под объектом, который уже получает меню из другого кабинета, написано «Сейчас меню из «…»», внизу — что произойдёт: сколько объектов получат меню, сколько перейдут из какого кабинета, что меню и сырьё нового кабинета пока пустые и где пригласить сотрудника бэк-офиса.
- Устройство: новый кабинет — организация `kind="directory"` со своим кодом справочника (`serviceCode`); отмеченные объекты получают `linkedServiceCode` = этот код. Один источник меню на объект сохраняется (пул = код), число пулов не ограничено. Старые кабинеты (привязанные к коду пищеблока) работают как раньше. Владелец аккаунта — участник кабинета (роль owner), журналы в кабинете выключены, как при прежнем создании.
- API `GET/POST /api/settings/master-cabinets` — только владелец аккаунта (как создание организаций); проверка названия (2–120), объектов только своего аккаунта, не больше 49 в кабинете (пул читает 50 вместе с кабинетом). Аудит `master_cabinet.created` (via: profile-menu) в текущей организации и в кабинете.
- `/api/organizations` отдаёт `canCreateMasterCabinet` для мини-приложения.
- «Настройки → Мастер-кабинет справочников»: в «Вопросах» — как завести ещё один кабинет. «Что нового»: пункт наверху раздела «Мастер-кабинет справочников», раздел поднят вторым.

Проверки: `src/lib/master-cabinet-choice.test.ts` (код пула, кабинет объекта, выбор по умолчанию, итог выбора, разбор id); e2e `e2e/create-cabinets.ts` на стенде 3021 с локальной e2e-базой (фикстура и откат в finally).

## Доступ к мастер-кабинету (30.09, вторая задача)

Запрос: «Сделать доступ другому человеку в мастер меню, у каждого меню свои настройки. Выбор из готовых сотрудников». Первый вариант (личный QR + PIN) владелец заменил: «вход через настройку прав у сотрудников, в этом разделе можно отправить приглашение на эл. почту, по которому происходит регистрация в организацию только с правами на конкретное мастер меню». Выбрано: оба способа — приглашение по почте и доступ уже заведённому сотруднику.

- «Настройки → Права доступа» — карточка «Мастер-кабинеты» (только владелец аккаунта; наверху страницы — ссылка «Доступ к мастер-кабинетам»). У каждого кабинета — люди со статусом: «Приглашён» / «Вошёл» (аккаунт только в кабинете) или «Сотрудник» (объект · должность).
- «Пригласить по почте»: ФИО + email → новый пользователь с домашней организацией-кабинетом (`role=manager`, неактивен до принятия), `InviteToken`, письмо «Мастер-кабинет «…» в WeSetup: установите пароль»; письмо не ушло — ссылка в ответе с кнопкой «Скопировать». Места тарифа проверяются как у обычного приглашения (`checkSeatsForActivation`, source `master-cabinet.invite`). Email уже занят в WeSetup — понятный отказ с подсказкой «Дать доступ сотруднику».
- «Дать доступ сотруднику»: сотрудники объектов аккаунта (активные, не в архиве) с поиском по имени, объекту и должности; «Рекомендуем — руководство и технологи» сверху. Выдача — `OrganizationMember(role=manager)`, уведомление в Telegram; кабинет появляется у сотрудника в меню профиля → «Кабинет».
- «Убрать» (ConfirmDialog с последствиями): сотруднику — снять участие, сбросить `lastActiveOrganizationId`, если это кабинет; приглашённому — архив и удаление ссылки; в обоих случаях `bumpSessionVersion` — сессии завершаются. `/api/master/*` дополнительно проверяет участие в кабинете.
- API `GET/POST/DELETE /api/settings/master-cabinets/access`, аудит `master_cabinet.access_granted` / `master_cabinet.invited` / `master_cabinet.access_revoked`.
- Окно «Новый мастер-кабинет» и тост после создания указывают, где выдавать доступ; «Что нового» — пункт наверху раздела «Мастер-кабинет справочников».

## Люди кабинета — сотрудники организаций (30.09, третья задача)

Переписка с заказчиком (Алексей): «А из МК если направлять? Сразу с ограничением прав? Он в сотрудниках не очень нужен». Решение владельца (Денис): «из МК можно будет направлять приглашение, но нужны стандарты и прозрачность, поэтому все должны быть в сотрудниках, но в своих группах. Там можно будет и настроить права доступов… при создании приглашения нужно указывать организацию. Можно пригласить из разных организаций. Те, которые не актуальны, закидываются в архив… расчёт по тарифу идёт по кол-ву сотрудников».

- `src/lib/master-cabinet-staff.ts` — общее ядро приглашения: сотрудник выбранной организации (`role=cook`, группа `JobPosition` «Мастер-кабинет» категории staff, создаётся при первом приглашении, права по умолчанию `["dashboard.view"]`), `journalAccessMigrated=true` без журналов, `lastActiveOrganizationId` = кабинет, `OrganizationMember(role=manager)` в кабинете, `InviteToken`. Повтор: ещё не вошёл / из архива той же организации / прежний аккаунт «только в кабинете» — новая ссылка; активный — «дайте доступ через «Дать доступ сотруднику»»; чужой email — отказ. Места тарифа — для нового и возвращаемого из архива (`checkSeatsForActivation` организации).
- Приглашение из кабинета: кнопка «Доступ» в шапке `/master` (только владелец аккаунта) → окно с тем же блоком, что в «Права доступа» (`CabinetAccessBlock`, API `/api/master/access` — кабинет берётся из сессии). Окно на слое 55 — под ConfirmDialog (60).
- «Права доступа → Мастер-кабинеты»: в приглашении выбор «Сотрудник какой организации» (по умолчанию — подключённая к кабинету); строка приглашённого — «Организация · Мастер-кабинет», статус «Приглашён» → «Сотрудник».
- `/settings/master-cabinet` (пищеблок): приглашение тоже создаёт сотрудника этой организации (с проверкой мест), список «Сотрудники кабинета» показывает и сотрудников организаций с доступом.
- Страница приглашения: у сотрудника организации с доступом к кабинету — плашка «Мастер-кабинет справочников «…»», после пароля сессия переключается на кабинет и открывается `/master`.
- «Убрать»: сотрудник группы «Мастер-кабинет» без других кабинетов — ещё и в архив (место тарифа освобождается).
- Общие обработчики API — `src/lib/master-cabinet-access-http.ts`; `MasterCabinetError` вынесен в `master-cabinet-error.ts` (без цикла импортов).
- Не сделано, ждёт решения владельца: предложение заказчика считать кабинет «+1 сотрудником» в каждом подключённом пищеблоке (сейчас в тарифе считается сам приглашённый — в своей организации).

## Тариф: кабинет = +1 сотрудник в каждом подключённом пищеблоке (30.09)

Предложение заказчика: «даём доступ — на организациях, к которым кабинет подключается, +1 сотрудник; отключился — −1». Владелец: «сейчас реализуем».
- `SEAT_USER_WHERE` не считает людей группы «Мастер-кабинет»; `master-cabinet-seats.ts`: кабинет с людьми (кроме владельца) добавляет по месту каждой организации аккаунта с тем же кодом справочника (`masterCabinetSeatsPerOrg`, тест). Учтено в `loadBillingUnit` и `listBillingUnits`.
- Проверка мест: при приглашении и выдаче доступа — `masterCabinetSeatsToAdd` (у кабинета ещё нет людей — число подключённых организаций, иначе 0).
