# ЭДО: входящие накладные (УПД) из Диадока, СБИС или файла → журнал приёмки (2026-10-31)

Заморожено 31.10.2026. Запрос владельца (идея № 16): «сделай … 16» — «ЭДО Диадок/СБИС: накладная пришла в
ЭДО — строка приёмки готова, осталось проверить товар».

## Что уже есть
- Приёмка из «Меркурия»: ВСД → строка журнала входного контроля (`incoming_control`): из документа —
  что, от кого, сколько, документы; температура, упаковка, органолептика и решение — только человек.
- ЭДО Saby для ROOT (исходящие договоры/счета/УПД платформы): JSON-RPC клиент по ключам приложения.
- Шифрование ключей интеграций AES-256-GCM (`integration-crypto.ts`).

## Решение
1. **Разбор УПД** (форматы ФНС 5.01–5.03, `ON_NSCHFDOPPR`, функции СЧФДОП/ДОП/СЧФ): номер, дата,
   продавец (ЮЛ/ИП, ИНН, КПП), строки (наименование, единица — из `НаимЕдИзм` или ОКЕИ, количество,
   цена, сумма), «годен до» строки, если поставщик его передал (`ИнфПолФХЖ2`), основание передачи.
   Кодировка из пролога (windows-1251 / UTF-8). Не УПД — понятная ошибка.
2. **Входящие накладные** — модель `SupplyDocument` (организация, источник `upload | diadoc | saby`,
   внешний id / хеш файла — без дублей, номер, дата, продавец, строки, статус `new | accepted |
   rejected | ignored`, кто и когда принял, документ журнала и строки приёмки).
3. **Приёмка накладной**: по каждой строке человек отмечает решение, температуру, упаковку,
   органолептику, «годен до», корректирующие действия; общие — время поставки, транспорт, документы.
   В действующий журнал приёмки (`ensureActiveDocument`) добавляются строки: продукт, поставщик,
   «УПД № … от … (Диадок/СБИС/файл)», объём — из документа, остальное — из проверки. Повторно принять
   нельзя.
4. **Подключения** — модель `SupplyEdoConnection` (организация × провайдер, ключи зашифрованы):
   - **Диадок**: ключ разработчика (`ddauth_api_client_id`), логин и пароль → токен, выбор ящика,
     входящие УПД `GetDocuments` → содержимое `GetEntityContent`;
   - **СБИС (Saby)**: ключи приложения, входящие документы реализации (`СБИС.СписокДокументов`, тип
     `ДокОтгрВх`) → XML вложения по ссылке.
   Загрузка — по кнопке «Проверить новые», при открытии входящих (не чаще раза в 15 минут) и маршрутом
   `/api/cron/edo-sync` (секрет `CRON_SECRET`) для серверного cron.
5. **Без подключения** — «Загрузить УПД (XML)»: файл из любого ЭДО.
6. **Страницы**: «Входящие накладные» `/edo` (список, загрузка, проверка новых), накладная
   `/edo/<id>` (строки и форма приёмки), настройки `/settings/integrations/edo`.

## Критерии приёмки
- **AC1** — разбор УПД 5.01 и 5.03 (ЮЛ и ИП, windows-1251 и UTF-8, единицы, «годен до»), отказ на чужой
  XML; тесты на образцах.
- **AC2** — строка приёмки из строки УПД: данные документа заполнены, физические поля пустые до проверки,
  проверка переносится; тест.
- **AC3** — `SupplyDocument`: загрузка файла без дублей (тот же файл → тот же документ), только своя
  организация; приёмка добавляет строки в журнал приёмки и закрывает накладную, повторная приёмка — отказ;
  «Не принимать» — без строк; права — как у журнала приёмки (руководство и те, кто ведёт приёмку).
- **AC4** — Диадок и СБИС: клиенты на подменённом транспорте — вход, ящики, список входящих УПД,
  скачивание и разбор, ошибки входа понятны; ключи хранятся только зашифрованными и наружу не отдаются;
  синхронизация не задваивает документы.
- **AC5** — страницы входящих, накладной и настроек в дизайн-системе, телефон без горизонтальной прокрутки;
  скриншоты.
- **AC6** — `typecheck`, `test:gate`, `eslint` по изменённым файлам, `i18n:check` — зелёные.

## Вне задачи
Подписание и отказ в ЭДО (титул покупателя), ТОРГ-12 отдельным форматом, сопоставление со справочником
продуктов и партиями, живые Диадок и СБИС (ключей нет — проверяется на подменённом транспорте).
