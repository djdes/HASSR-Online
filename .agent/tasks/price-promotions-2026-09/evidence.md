## Что сделано (по пунктам spec)

1. **Акции (AC1).** Модель `PricePromotion` (title, percent 1–90, startsAt/endsAt, active, note). ROOT → «Деньги
   и продажи» → **«Акции»** (`/root/promotions`): блок «Сейчас на сайте» (какая акция действует и как клиенты
   видят цену), группы «Идут сейчас / Будущие / Прошедшие», форма создать/изменить (дата и время по МСК,
   кнопки «сейчас», «7/14/30 дн.», живое превью цены), «Выключить/Включить», «Удалить» (ConfirmDialog, danger),
   статусы «Действует / Перекрыта большей скидкой / Запланирована / Завершена / Выключена», оплаты и сумма
   скидок по каждой акции, «История изменений». Проверки: название, процент — целое 1–90, конец позже начала;
   сервер читает время строкой «ГГГГ-ММ-ДДTЧЧ:ММ» как московское (`mskInputToDate`, UTC+3 без Intl).
   Пересечение окон допустимо — действует наибольший процент (при равных — та, что кончается позже).
   Граница: начало включительно, конец — нет.
2. **Одна серверная функция цены.** `getSubscriptionOffer(now, tariffKey)` (`src/lib/promo/offer.ts`): база из
   `PlatformTariff`, действующая акция, цена со скидкой в целых рублях, конец акции; `null` — тариф снят.
   Витрины берут то же через `getDisplayOffer(tariff)` (сбой чтения акций → без акции, страница не падает).
   Чистый client-safe расчёт — `src/lib/promo/promotions.ts`: `applyPromotion(amount, promotion)` (для любой
   суммы подписки, в т. ч. база + доплата сверх лимита), `computeCheckoutAmounts` (акция → промокод от цены
   с акцией → оборудование), `pickActivePromotion`, МСК-время, подписи плашки.
3. **Зачёркнутая цена (AC2)** — один компонент `PromoPrice` (+`PromoBadge`), `src/components/pricing/promo-price.tsx`,
   без хуков (работает и в серверных, и в клиентских деревьях). Места:
   - лендинг: строка цены в первом экране (телефон и компьютер), карточка «Подписка» (`PlanCard price=`),
     калькулятор оборудования (итог «Подписка»), JSON-LD `Offer.price` = цена по акции + `priceValidUntil`;
   - `/pricing`: цена в тексте, карточки «Подписка» и «Подписка + оборудование», ROI-калькулятор;
   - `/settings/subscription` (он же «Тарифы и оплата» в Telegram Mini App): карточка «Подписка», калькулятор
     оборудования, «Оплата по безналу» (счёт на цену по акции), «Как считается стоимость» (текст, «В месяц»
     — со скидкой на всю сумму подписки, строка «Сейчас акция …»);
   - `/order`: строка «Подписка на N дн.» (старая зачёркнута, новая, плашка), итог «К оплате»;
   - ROOT: превью в форме и «Сейчас на сайте»; в карточке организации у оплат — «акция −N % (−X ₽)» и промокод.
   Поиск мобильных/мини-экранов: в `src/app/mini` цены подписки нет (₽ только у бонусов), пункт «Тарифы и
   оплата» Mini App открывает `/settings/subscription`; приложение (Capacitor) цен и оплаты не показывает
   (правила сторов: `/order`, `/pricing` уводят домой, `/settings/subscription` — только статус). Письма и бот
   цену подписки не пишут (только фактическую сумму оплаты). Автопродление («Следующее списание … на X ₽»)
   оставлено по цене тарифа: это будущее списание, акция к его дате может кончиться.
4. **Оплата.** `POST /api/payments/robokassa/create`: `getSubscriptionOffer` → промокод от цены с акцией
   (`resolvePromo`, `computeDiscountRub`) → `computeCheckoutAmounts` → баллы → заказ. В `PaymentOrder`
   снимком: `baseRub`, `promotionId`, `promotionPercent`, `promotionDiscountRub`, `promoCode`, `discountRub`;
   описание (оно же в чеке/УПД/ответе) — «Подписка на 30 дн. (акция «…» −20 %; промокод X: −159 ₽)». Чек
   Робокассы — итоговая сумма заказа. Защита «цена изменилась»: клиент присылает `expectedGrossRub` (сверка,
   не сумма) — если за время на странице акция началась/кончилась, 409 `price-changed`, страница
   пересчитывается. Счёт по безналу — по той же цене с акцией (снимок в заказе). УПД: «Скидка по акции
   (−20 %): 398 ₽. Промокод …».
5. **Промокоды (AC3)** — путь проверен целиком (ROOT создаёт → клиент вводит → проверка → поверх акции →
   учёт после оплаты). Найдено и починено — см. раздел «Промокоды: проверка пути». Стартовый набор —
   `src/lib/promo/starter-codes.ts` + `scripts/seed-promo-codes.ts` (идемпотентный, создаёт ВЫКЛЮЧЕННЫМИ,
   без `--apply` — сухой прогон).
6. **Логи и аудит.** `console.info("[promo] …")`: создание/изменение/удаление акции, проверка кода (принят/
   отклонён с причиной, без почты), расчёт заказа и счёта, отказ «цена изменилась», сид кодов. Аудит:
   `AuditLog` (организация `platform`, сущность `PricePromotion`, действия `promotion.create/update/enable/
   disable/delete`, «было → стало» по-русски, время по МСК) — видно в «Акции → История изменений» и в
   `/root/audit` (подписи добавлены).

## Промокоды: проверка пути (что было не так и как починено)

| # | Проблема | Починка | Проверка |
|---|---|---|---|
| 1 | Скидка промокода считалась от цены тарифа, а не от цены с акцией | `resolvePromo(…, subscriptionRub: offer.priceRub)` + `computeCheckoutAmounts` | unit + e2e (1592 − 10 % = 1433) |
| 2 | Использования считались только по `status = paid`; после достройки профиля новым клиентом заказ становится `completed` и выпадал из счётчика — лимит кода можно было превысить, таблица ROOT занижала оплаты | `PAID_ORDER_STATUSES = [paid, completed]` в `resolvePromo`, `promoPaidUses` | e2e: код с лимитом 1, оплата → `completed` → «использован максимальное число раз» |
| 3 | «Только новым» обходился: выйти из кабинета и оформить заказ на почту постоянного клиента (организация = null → «новый») | проверка и по почте заказа, и по организации, которой почта принадлежит (`hasPaidOrders`) | e2e: 400 «только для новых клиентов» без входа; новая почта — скидка есть |
| 4 | ROOT-форма: дата «до» бралась в часовом поясе браузера, «с» не задавалась, в таблице был только конец | срок по МСК (`с 00:00` / `по 23:59:59`), поле «Действует с», колонка «Срок (МСК)» | снимок таблицы |
| 5 | Промокод на 100 %: кнопка «Оплатить баллами», в заказе `paidBy: points` без баллов | «Оформить без оплаты», `paidBy: discount` | код |
| 6 | Статус `completed` в истории оплат показывался сырым словом | «оплачен» (`orderStatusLabel`) | код |

Осталось (не чинил, риски): гонка лимита — два неоплаченных заказа с кодом на 1 использование могут оба
оплатиться (лимит проверяется при создании заказа, деньги после оплаты не вернуть — нужна бронь); тестовые
оплаты (`isTest`) считаются в лимит кода, а в «только новым» — нет (как было); возвраты (`refundedAt`) лимит
не освобождают (консервативно).

## Схема (аддитивно)

- новая модель `PricePromotion` (+ индекс `active, endsAt`);
- `PaymentOrder`: `baseRub Int?`, `promotionId String?`, `promotionPercent Int?`,
  `promotionDiscountRub Int @default(0)`, индекс `promotionId`.
Прод: `prisma db push` в деплое применит без потери данных.

## Не делал / открытые вопросы

- Автосписания (рекуррент) в коде ещё не реализованы; когда появятся — сумму брать из `getSubscriptionOffer`
  на дату списания, а не повторять сумму первого платежа.
- Закрывающие документы и строка «Документы» в истории оплат доступны только для `status = paid`; заказы
  `completed` (новый клиент достроил профиль) их не получают — старое поведение, вне задачи.
- Окно перехода (задача billing) показывает цену тарифа как есть; подключить `getDisplayOffer` + `PromoPrice`
  — после слияния.
- whats-new / CHANGES не трогал (по заданию).
