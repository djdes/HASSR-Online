# Смоук «04-acceptance: нет ошибок страницы» — причина и исправление (AC4)

## Симптом

Ночной браузерный смоук (`.github/workflows/nightly-e2e.yml`, `next dev -p 3005`) изредка падал на шаге
`04-acceptance: нет ошибок страницы`: React сообщал «A tree hydrated but some attributes of the server rendered HTML
didn't match the client properties» — у кнопки переключателя объекта в шапке (`DropdownMenuTrigger`, Radix) сервер
отдал `id="_R_4b345rlabmilb_"`, а клиент при гидратации посчитал `_R_12op1etabmilb_`.
Падение до правки: `smoke-run2-before-fix.log` (локальный `npm run smoke:local`, тот же шаг).

## Разбор

1. Идентификаторы `useId` строятся из пути по дереву: у каждого списка детей (массива) React добавляет «развилку»
   (сколько детей, какой по счёту). Сервер (Fizz) и клиент должны пройти одинаковые развилки.
2. Снят путь волокон до кнопки в момент гидратации (подставной хук DevTools) — 116 уровней, 28 развилок. Модель
   алгоритма по этому пути даёт ровно серверный `id`. Клиентский `id` получается, если убрать **одну** развилку
   «2 ребёнка, второй» на одном из уровней 54–69: фрагмент сегмента макета кабинета под `SegmentViewNode`,
   `DomainMessagesProvider`, `JournalControlsProvider`, `CustomNamesProvider`, `SiteThemeProvider`.
3. В `next dev` Next оборачивает каждый макет в `SegmentViewNode` (обозреватель сегментов DevTools), который отдаёт
   `[узел обозревателя, children]` — фрагмент сегмента становится вторым ребёнком, с флагом `Forked`. Его дети —
   `[ресурсы слоя, <макет>]`; асинхронный макет и клиентские модули приходят в RSC «ленивыми» строками.
4. Если при гидратации ленивая строка ещё не разобрана и разбирается в микрозадаче, React повторяет работу волокна
   (`replayBeginWork`). Для фрагмента, хост-узла и ленивого компонента повтор идёт через `unwindInterruptedWork`
   (снимает развилку этого волокна) и `resetWorkInProgress`, который оставляет только статические флаги
   (`flags &= 132120578`) — а `Forked` (`1 << 20`) в эту маску не входил. Повторный `beginWork` уже не видит
   `Forked` и не возвращает развилку: все `useId` ниже получают другой путь → несовпадение атрибутов.
5. Ошибка React, исправлена в facebook/react#35518 «[Fiber] fix useId tracking on replay» (16.01.2026): `Forked`
   добавлен в статическую маску. Рядом — facebook/react#35494 (повтор при гидратации и курсор гидратации).
   В Next 16.1.7 встроен React `19.3.0-canary-f93b9fd4-20251217` — без исправлений; в Next 16.2.12 —
   `19.3.0-canary-3f0b9e61-20260317` с обоими (маска `133169154`, сброс курсора в `replayBeginWork`).

## Детерминированное воспроизведение (`repro/`, вывод — `repro-output.txt`)

Минимальное дерево как у Next в dev: `SegmentViewNode` → `[<i/>, <Fragment key>]` → `[<link/>, ленивый ребёнок]` →
кнопка с `useId`. Сервер рендерит той же сборкой React, клиент гидратирует в Chromium внутри `startTransition` (как
`app-index.js` у Next); ленивый ребёнок разрешается в микрозадаче после первой приостановки.

- React из Next 16.1.7: сервер `_R_a_`, клиент `_R_2_` — «HYDRATION MISMATCH» (потеряна ровно развилка фрагмента).
- React из Next 16.2.12: `_R_a_` и `_R_a_`, ошибок гидратации нет.

## Исправление

`next` и `eslint-config-next` 16.1.7 → 16.2.12 (точные версии, `package-lock.json` меняется только у пакетов Next).
Обход в тесте не делался, проверка «нет ошибок страницы» не ослаблялась.
