# Spec (frozen 2026-11-19): обмен справочниками с чужим аккаунтом — запрос по коду мастер-кабинета и подтверждение по почте

Часть 3 из трёх (дизайн: docs/superpowers/specs/2026-11-19-multi-org-trial-sync-design.md; часть 2 —
`.agent/tasks/org-exchange-2026-11-19/`).

Запрос владельца: «если ввести ID мастер кабинета организаций вообще из других аккаунтов, будет предложено точно так же
установить связь синхронизацию или импорт точечно, но уже должно придти на почту другого пользователя оповещение, где
сама организация находится, через подтверждение. Пользователь который запросил — ему пишется что ожидайте».

## Исходное состояние (после части 2)
- Обмен справочниками и разовый перенос работают только между организациями одного аккаунта (`run.server.ts`:
  участник чужого аккаунта отбрасывается, перенос требует `from.accountId === to.accountId`).
- Мастер-кабинет имеет код `Organization.serviceCode` вида `ABCDE-FGH23` (`dish-pool-code.ts`).
- Письма: `sendRawEmail` + `renderEmailLayout` (`src/lib/email.ts`); токены приглашений — случайная строка, в базе
  только SHA-256 (`src/lib/invite-tokens.ts`).

## Решения
- Р1. Запрос создаёт владелец аккаунта на платном тарифе (в пробном и на бесплатном — отказ: иначе новая почта плюс
  перенос данных дают бесконечный пробный период). Ввод — код мастер-кабинета; кабинет своего аккаунта не подходит
  («это ваш кабинет»). Код не найден — один и тот же ответ, без подсказок.
- Р2. `DirectoryExchangeRequest`: кабинет, организация-заявитель, кто запросил, режим (`link` | `transfer`), списки,
  SHA-256 токена, статус (`pending` | `approved` | `declined` | `cancelled` | `expired`), срок 7 дней, что разрешено.
  Один открытый запрос на пару «кабинет — организация»; не больше 5 запросов в сутки на аккаунт.
- Р3. Владельцу аккаунта кабинета уходит письмо: кто просит (название, ИНН), что (связь или перенос, какие списки),
  кнопка «Открыть запрос». Страница `/exchange-request/<токен>` требует входа под владельцем аккаунта кабинета; он
  отмечает, какие списки разрешает (не шире запрошенных), для переноса выбирает свою организацию-источник, и
  подтверждает либо отклоняет.
- Р4. Подтверждение связи: организация-заявитель становится участником обмена этого кабинета с разрешёнными списками;
  обмен запускается сразу. Подтверждение переноса: разовый перенос из выбранной организации в организацию-заявителя.
- Р5. Между аккаунтами сотрудники переносятся только как ФИО и должность: телефон и выходные не передаются и не
  сравниваются, если среди участников списка есть организация другого аккаунта.
- Р6. Заявитель видит «Ожидает подтверждения» (кому отправлено — название кабинета, до какого числа) и может отменить.
  После решения — уведомление в кабинете и письмо. Обе стороны могут разорвать связь: заявитель — выйти, владелец
  кабинета — отключить участника.
- Р7. Каждое действие — в аудите обеих сторон (`directory_exchange.request_*`).

## Устройство (контракты для реализации)

### Схема (`prisma/schema.prisma`, только добавление)
```prisma
model DirectoryExchangeRequest {
  id                      String       @id @default(cuid())
  masterOrganizationId    String
  masterOrganization      Organization @relation("DirectoryExchangeRequestMaster", fields: [masterOrganizationId], references: [id], onDelete: Cascade)
  requesterOrganizationId String
  requesterOrganization   Organization @relation("DirectoryExchangeRequestRequester", fields: [requesterOrganizationId], references: [id], onDelete: Cascade)
  requestedByUserId       String
  mode                    String       // link | transfer
  kinds                   String[]     @default([])
  tokenHash               String       @unique
  status                  String       @default("pending") // pending | approved | declined | cancelled | expired
  expiresAt               DateTime
  decidedAt               DateTime?
  decidedByUserId         String?
  allowedKinds            String[]     @default([])
  sourceOrganizationId    String?      // перенос: из какой своей организации владелец кабинета разрешил взять
  resultJson              Json?
  createdAt               DateTime     @default(now())
  updatedAt               DateTime     @updatedAt
  @@index([requesterOrganizationId, status])
  @@index([masterOrganizationId, status])
}
```
и поле `DirectoryExchangeMember.foreign Boolean @default(false)` — участник из другого аккаунта, добавленный
подтверждённым запросом.

### Движок (`src/lib/directory-exchange/`)
- Участник с `foreign = true` участвует в обмене кабинета, хотя его аккаунт другой; остальные правила участника те же
  (не демо, не кабинет, не закрыт, не на паузе).
- Р5: если среди участников списка «Сотрудники» есть участник с `foreign`, у сотрудников обмениваются только ФИО и
  должность — телефон и выходные не читаются в отпечаток, не создаются и не обновляются. То же в переносе между
  аккаунтами.
- `transferOnce`/`transferPreview` получают явный параметр, разрешающий пару организаций из разных аккаунтов; без
  него поведение прежнее (404). Параметр передаёт только код подтверждения запроса.
- Чистые правила — `src/lib/directory-exchange/requests.ts`: `decideRequestCreation`, `decideRequestDecision`,
  `narrowAllowedKinds`; серверная часть — `requests.server.ts`.

### API
- `POST /api/settings/directory-exchange/requests { code, mode: "link"|"transfer", kinds }` → `{ ok: true, request }`,
  где `request = { id, cabinetName, mode, kinds, status, expiresAt, createdAt }`. Отказы: 400 — код не похож на код;
  404 — «Мастер-кабинет с таким кодом не найден» (и для несуществующего, и для демо); 409 — свой кабинет, уже есть
  открытый запрос, организация уже участник; 402 — аккаунт не на платном тарифе; 429 — лимит.
- `GET /api/settings/directory-exchange/requests` → `{ outgoing: request[], foreignLinks: Array<{ id, cabinetName,
  kinds, since }>, incoming: Array<{ id, requesterName, mode, kinds, expiresAt, createdAt }>, foreignMembers:
  Array<{ organizationId, name, kinds, since }> }` — `outgoing` и `foreignLinks` для активной организации;
  `incoming` и `foreignMembers` — для кабинета аккаунта, если человек его владелец.
- `DELETE /api/settings/directory-exchange/requests/[id]` — заявитель: отменить открытый запрос или выйти из
  подтверждённой связи; владелец кабинета: отключить участника из другого аккаунта. → `{ ok: true }`.
- `GET /api/exchange-requests/[token]` → `{ request: { id, requesterName, requesterInn, mode, kinds, status,
  expiresAt }, cabinet: { id, name }, sources: Array<{ id, name }> }` — только владельцу аккаунта кабинета; иначе 403
  с понятным текстом; неизвестный токен — 404.
- `POST /api/exchange-requests/[token] { decision: "approve"|"decline", allowedKinds?, sourceOrganizationId? }` →
  `{ ok: true, status, summary? }`. Повторное решение, истёкший срок — 409.

### Письма и уведомления
- Владельцу аккаунта кабинета — при создании запроса (`sendRawEmail` + `renderEmailLayout`, ссылка
  `<APP_URL>/exchange-request/<токен>`); заявителю — при решении; заявителю в колокольчик — `Notification`.
  Отправка в try/catch, после ответа.

### Интерфейс
- Тексты — `dashboardUi.directoryExchange.foreign.*` (ru/en/uz).
- Окно «Связать или перенести данные»: блок «Другая компания» — поле кода мастер-кабинета, кнопка «Отправить запрос»
  (режим и списки — те же, что выбраны в окне); после отправки и при открытии — «Ожидает подтверждения владельца
  мастер-кабинета «…», до <дата>» с «Отменить запрос»; подтверждённая связь — «Связано с мастер-кабинетом «…»» с
  «Выйти из обмена».
- Строка-предложение и карточка показывают ожидающий запрос; карточка владельца кабинета — входящие запросы
  («Открыть запрос») и участников из других аккаунтов с пометкой «другой аккаунт» и «Отключить».
- Страница `/exchange-request/[token]`: вне кабинета, требует входа (без входа — на `/login` с возвратом); карточка
  запроса, галочки разрешаемых списков (по умолчанию — запрошенные), для переноса — выбор своей организации-источника,
  кнопки «Подтвердить» и «Отклонить», итог.

## Критерии приёмки
- AC1. Чистые правила с тестами: можно ли создать запрос (тариф, свой кабинет, лимит, дубль), можно ли решить
  (статус, срок, кто решает), сужение разрешённых списков.
- AC2. Схема: одна новая таблица, `prisma db push` без потери данных.
- AC3. API: создать запрос по коду, список своих запросов, отмена; чтение запроса по токену и решение — только
  владельцу аккаунта кабинета; чужой токен, истёкший срок, повторное решение — отказ.
- AC4. Письмо владельцу кабинета со ссылкой; письмо и уведомление заявителю о решении. Сбой почты запрос не ломает.
- AC5. Подтверждённая связь: обмен идёт между аккаунтами по разрешённым спискам; у сотрудников между аккаунтами нет
  телефона (Р5). Подтверждённый перенос: данные из выбранной организации появились у заявителя, связь не сохранена.
- AC6. Интерфейс: поле «Код мастер-кабинета другой компании» в окне «Связать или перенести», состояние «Ожидает
  подтверждения» с отменой; страница подтверждения; в карточке обмена — участники из других аккаунтов с пометкой и
  «Отключить».
- AC7. Тексты ru/en/uz; typecheck, test:gate, i18n:check; живой прогон двух аккаунтов: запрос → письмо (в журнале
  dev-сервера) → подтверждение → данные обменялись; отклонение; отмена; пробный аккаунт получает отказ.
